# 第 4 章：function calling → MCP → A2A 的演进脉络

> 理解这三个东西的关系，最好的方式是看它们怎么一步步演进。
> 结论：**不是替代关系，是层层叠加**。

---

## 4.1 演进时间线

```
2023.06  OpenAI 推出 function calling
    ↓ 工具激增 → M×N 集成爆炸
2024 末  Anthropic 开源 MCP
    ↓ 工具生态平台化
2025.04  Google 推出 A2A
    ↓ agent 间协作标准化
2025+   A2A 移交 Linux Foundation，逐步成熟
```

---

## 4.2 阶段①：function calling（2023.06）

### 它解决了什么

OpenAI 推出 function calling：模型输出**结构化 JSON** 调外部工具。

之前要工具调用，只能靠 prompt engineering（让模型输出特定格式文本，再正则解析），脆弱。function calling 让模型原生输出结构化调用请求。

### 它是什么

「**单次调用语义**」——模型说「调这个函数」，程序执行，结果回去。

```json
{"name": "get_weather", "arguments": {"city": "北京"}}
```

### 局限

每个工具要在每个框架里**单独适配**。3 个 LLM × 5 个工具 = 15 套定制集成。

---

## 4.3 阶段②：MCP（2024 末）

### 痛点：M×N 集成爆炸

工具激增导致集成爆炸。每个 Agent 框架的工具接口各不相同，写一个工具要适配 N 次。

### MCP 的解法

定义**统一协议**，在 function calling 之上加了：
1. **动态发现**：client 连上 server 后动态发现工具，不硬编码
2. **标准化**：JSON-RPC + 统一 schema
3. **规模化**：一个 server 暴露的工具，所有 MCP client 都能用

### 关键区别

- **function calling** 是「单次调用语义」——模型说调函数，程序执行
- **MCP** 是「工具的发现/连接/运行的标准协议」——在 function calling 之上加动态发现 + 标准化

**MCP 不是替代 function calling，是把工具生态从点对点集成变成平台化**。MCP server 内部最终还是要用 function calling 让模型调工具。

---

## 4.4 阶段③：A2A（2025）

### 痛点：agent 间协作没标准

MCP 解决了 agent↔tool，但 agent↔agent 还没标准。每个框架用自己的多 agent 机制（AutoGen GroupChat、OpenAI handoff、CrewAI 角色）。

### A2A 的解法

把「工具协议」扩展到「agent 协议」。定义 agent 间互相发现（Agent Card）、通信（JSON-RPC）、协作（Task 状态机）的标准。

### 关键扩展

从 MCP 的「被动工具」到 A2A 的「对等 agent」。工具是函数调用，agent 是有状态的协作实体。

---

## 4.5 ★ 三者的层次关系（核心图）

```
A2A（agent 间协作）
   ↓ 委派的子任务
MCP（agent 用工具）
   ↓ 实际调用
function calling（模型输出 JSON）
```

**它们是层层叠加，不是替代**：

- 最底层 **function calling**：模型输出结构化调用请求
- 中间层 **MCP**：工具的发现/连接/运行的标准化
- 最上层 **A2A**：agent 间协作的标准化

### 一个完整调用栈

```
Agent A 想翻译 →
  A2A 委托给翻译 Agent B →
    Agent B（A2A server）接收 task →
      Agent B（MCP client）调用 translate 工具 →
        translate 工具内部：function calling 让 B 的 LLM 决定怎么调 →
          实际执行翻译 →
        结果返回 B →
      B 返回 task 结果 →
    A2A 把结果给 A →
  A 继续工作
```

四层全用上了：A2A（A↔B）+ MCP（B↔工具）+ function calling（B 的 LLM 决策）。

---

## 4.6 Self-Agent 用了哪几层

Self-Agent 同时用三层：

| 层 | Self-Agent 怎么用 |
|---|---|
| **function calling** | agent_node 让 LLM 决定调哪个工具（全书第 5、6 章） |
| **MCP** | 接外部工具（client）+ 暴露自身工具（server）（全书第 10 章） |
| **A2A** | delegate_to_agent 委托外部 agent + 被 external agent 调用 |

**这就是「协议驱动」Agent 的完整形态**——不靠单一框架，靠标准协议栈接入生态。

---

## 4.7 演进的启示

1. **标准化是趋势**：从点对点集成到平台化，每层协议都在降低集成成本
2. **不替代，是叠加**：新协议不杀老协议，是在上面加一层
3. **工具 → agent 是自然延伸**：MCP 解决「agent 用工具」，A2A 自然延伸到「agent 用 agent」
4. **生态价值 > 单点优化**：一个 server/tool/agent 实现一次协议，所有 client 都能用

---

## 4.8 给 Self-Agent 的启示

Self-Agent 已经用了完整的三层协议栈，这是对的。这章主要是**理解演进脉络**，知道每个协议解决哪层问题。

### 一个观察

未来可能出现更多协议层（如 agent 编排协议、agent 商业协议）。Self-Agent 的「协议驱动」架构让它能灵活接纳新协议——只要新协议出现，加一层适配即可，不用动内核。
