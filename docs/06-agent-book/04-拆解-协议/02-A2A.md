# 第 2 章：A2A（Agent2Agent Protocol）

> 让不同框架/厂商构建的 AI agent **互相发现、通信、协作**的开放标准。
> 2025 年 4 月 Google 发布，后移交 Linux Foundation。是 Self-Agent 多 Agent 层基石。

---

## 2.1 它是什么

地址 github.com/a2aproject/A2A、a2a-protocol.org。2025 年 4 月 Google 发布，后移交 Linux Foundation 治理。

类比：**MCP 是 USB-C（工具接口），A2A 是 HTTP（服务器互通）**。

---

## 2.2 ★ Agent Card：数字名片（核心概念）

JSON 元数据，描述 agent 的能力/技能/端点/鉴权要求。放在 `/.well-known/agent-card.json`（对齐 RFC 8615）。

### DNS 式去中心化发现

**一次无鉴权 GET 即可发现**：

```http
GET https://translator-agent.example.com/.well-known/agent-card.json
```

```json
{
  "name": "翻译 Agent",
  "description": "多语言翻译",
  "version": "1.0",
  "capabilities": {"streaming": true, "pushNotifications": false},
  "skills": [{"id": "translate", "name": "翻译"}]
}
```

外部 Agent 读 Card 决定是否调用、怎么调用。

### 为什么放 well-known

对齐 RFC 8615（`/.well-known/` 是 web 标准的「众所周知路径」，如 `/.well-known/security.txt`）。这样任何 agent 都知道去哪找 Card，不用中心注册——像 web 的 robots.txt。

---

## 2.3 任务模型

A2A 的核心工作单元是 **Task**，有状态机：

```
submitted → working → completed
                ↓
          input-required（需要用户输入）
                ↓
          working ...
```

- **Task**：工作单元
- **Message**：一轮对话，含 role 和 Parts
- **Part**：内容块（text / data / file）

---

## 2.4 传输

**JSON-RPC 2.0 over HTTP**，流式用 **SSE**。

核心方法：
- `tasks/send`：发送任务
- `tasks/get`：查任务状态
- `tasks/sendSubscribe`：发送 + 订阅流式更新
- `tasks/:id/cancel`：取消任务

---

## 2.5 Self-Agent 怎么用 A2A（双向）

### 作为 Server（`app/a2a/server.py`）

`mount_a2a(app)` 把路由挂到 FastAPI。`SelfAgentExecutor`（`a2a/executor.py`）把 `run_agent` 包装成 A2A 任务执行器——别的 Agent 可通过 A2A 协议调用本 Agent。

### 作为 Client（`app/a2a/client.py`）

`call_remote_agent(base_url, message)`。还有 `delegate_to_agent` 工具——LLM 自主决定何时委托外部 Agent。

```
用户：「帮我翻译这段话并总结」
  ↓
本 Agent：识别需要翻译 → delegate_to_agent("http://translator:8001", 原文)
  ↓
翻译 Agent：返回译文
  ↓
本 Agent：拿到译文 → 整合总结 → 回复用户
```

---

## 2.6 ★ 不透明对等体（核心设计）

A2A 的核心：Agent 间**共享输入输出，不共享内部**（工具、记忆、状态）。

### 为什么

解耦与异构。只要遵守 A2A 协议（输入消息、输出回复），**任意实现都能互通**，像 HTTP 让任意服务器互通一样。不需知道对方用什么框架/LLM/存储。

### 对比 MCP 的「透明」

MCP 的工具是**被动**的——client 知道工具的 schema、参数、返回。工具没有自主性。

A2A 的 agent 是**对等**的——双方都有 LLM/记忆/工具，各自自主决策。client 不知道 server 内部怎么工作，只看到输入输出。

---

## 2.7 版本差异（a2a-sdk 1.1.x / v1.0 协议）

与早期 v0.3 的差异：
- Agent Card 路径：`/.well-known/agent-card.json`（非 `agent.json`）
- 消息类型：protobuf 风格（`Part(text=...)`）非 pydantic
- 端点：REST 风格（`/message:send`）非纯 JSON-RPC

Self-Agent 用 a2a-sdk 1.1.x + v1.0 协议。

---

## 2.8 ★ delegate_to_agent 的安全考量

委托外部 Agent 的风险：**信任与安全**。无法保证输出质量/安全。

### 风险

- 外部 agent 可能返回错误/有害内容
- 外部 agent 可能被注入（返回恶意指令）
- 外部 agent 可能超时/不可用

### Self-Agent 当前防护

- 超时控制（60s）
- 错误兜底

### 生产应加（借鉴方向）

- **白名单**：只委托可信 Agent（不能让 LLM 随便 delegate 到任意 URL）
- **输出校验**：对委托结果做 schema/内容校验
- **审计日志**：记录所有委托
- **限流**：限制委托频率防滥用

---

## 2.9 A2A 的批判视角（诚实）

A2A 不是银弹。社区有批判声音（如 blog.fka.dev「What happened to Google's A2A」）：
- 协议还在演进，稳定性待观察
- 实际采用率待验证
- 与 MCP 的边界有时模糊

**Self-Agent 用 A2A 的态度**：作为多 Agent 协作的标准化方向，但承认它还在成熟中。

---

## 2.10 给 Self-Agent 的借鉴

### 借鉴①：delegate 白名单 + 输出校验

当前 delegate 只有超时。生产应加信任列表 + 结果校验（第 2.8 节）。

### 借鉴②：Agent Card 的 skills 用于自动路由

根据 Card 的 skills 字段自动决定委托哪个 Agent，而不是靠 LLM 自己猜。比如用户说「翻译」，系统查所有已知 Agent Card 的 skills，自动找到有「translate」skill 的 agent。

### 借鉴③：A2A server 注册中心

当前 A2A 是点对点（知道 URL 才能调）。可加一个注册中心，agent 启动时注册 Card，client 从注册中心发现。但这牺牲了去中心化，权衡要慎重。
