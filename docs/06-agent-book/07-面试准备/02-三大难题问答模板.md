# 面试准备②：三大难题问答模板

> 幻觉、上下文漂移、缓存命中——这是 LLM/Agent 岗面试**最高频的三块**。
> 每个难题给你一套「一句话答 → 展开答 → 追问链 → 答不上来的诚实兜底」。

---

## 怎么用这一篇

面试官问这类题，通常按这个套路深挖：
1. **是什么**（概念）
2. **为什么会有**（根因）
3. **怎么治**（方案）
4. **你的项目怎么做的**（落地）
5. **还能怎么改进**（深度）

你按这个 5 层结构答，每一层都准备好，就不会被追到死角。

## 难题一：幻觉（Hallucination）

### 一句话答
幻觉是 LLM 生成看似合理但错误的内容，根因是预训练的固有副产物（OpenAI 2025 论文定性），治法是 RAG + 函数调用 grounding + 结构化输出三件套，高可靠场景加多 Agent critic 互验。

### 展开答（5 层）

**① 是什么**：LLM 编造不存在的事实/工具/格式。分三类——事实幻觉（编造 API）、工具幻觉（调不存在的函数，GPT-4 仍犯）、格式幻觉（畸形 JSON）。

**② 为什么会有**：
- 训练目标是"下一个 token 概率最大"，不是"事实正确"。模型擅长流畅，不擅长知道边界。
- **反直觉点**（加分）：2025 arXiv 发现**增强推理反而放大 tool hallucination**——模型越会想，越容易自信地编造函数名。这是 trade-off。

**③ 怎么治**（按性价比）：
- **RAG**（baseline）：检索文档塞 prompt，让回答基于文档。Self-reflective RAG 幻觉率降到 5.8%（学术）。
- **函数调用 grounding**：答案必须来自工具返回，而非自由生成。OpenAI 2025 论文：grounding 是必需不是可选。
- **结构化输出**：JSON Schema 约束输出格式。⚠️ **关键认知**：治格式幻觉不治内容幻觉——合法 JSON 仍可能含编造的 order_id。
- **进阶**：CRAG（检索评估器兜底）、Citation（强制引用来源）、多 Agent critic 互验（跨厂商避免同源偏见）。

**④ 你的项目怎么做的**：
- 做了 function calling（算半个 grounding）、可选 RAG
- 刚加了结构化输出契约（response_format）
- 缺 citation 和 critic（诚实承认，接改进方向）

**⑤ 还能怎么改进**：加 CRAG 兜底 + 跨模型 critic（GLM 生成、Qwen 校验）+ Citation prompt 模拟。

### 追问链（提前准备）
- 「RAG 检索失败怎么办？」→ CRAG 加评估器，低分触发 web 搜索兜底
- 「结构化输出能治内容幻觉吗？」→ 不能，只治格式。内容要靠 grounding + critic
- 「为什么增强推理放大 tool hallucination？」→ 推理强→更自信→更敢编（arXiv:2510.22977）

### 答不上来的诚实兜底
> "幻觉的学术根因我没有深挖，但工程上我理解三件套治法——RAG、grounding、结构化输出。我的项目做了后两个，RAG 在做。"

## 难题二：上下文漂移（Context Drift）

### 一句话答
长对话/长任务中 agent 逐渐忘记目标、被中间信息带偏。治法是滑动窗口摘要 + 外部 plan 记事板 + Plan-and-Execute 分解，2025 有个新概念叫 Context Engineering。

### 展开答（5 层）

**① 是什么**：长任务走到第 7、8 步，agent 偏离最初目标、重复执行、被无关结果带跑。根因是 LLM 看完所有历史再决定，历史越长关键信号越被稀释。

**② 为什么会有**：注意力机制对长上下文的"有效利用度"会下降（中间内容被淹没，所谓 lost in the middle）。

**③ 怎么治**：
- **滑动窗口摘要**（baseline）：早期对话压缩成摘要，保留最近 N 条完整。
- **外部 plan 记事板**：把待办写到外部结构，每轮只读相关部分，不靠 LLM 记。
- **Plan-and-Execute**：先规划再分步，或拆给子 Agent（Aider Architect/Editor 是精致版）。
- **Context Engineering**（2025 新概念，加分词）：不是写好 prompt，而是系统工程地为 LLM 准备合适的上下文——什么进、什么出、什么格式、何时压缩、何时检索。LangChain 总结了 4 种失效模式：context poisoning（错误信息混入）、poverty（该有的没有）、distraction（信息太多）、conflict（矛盾）。

**④ 你的项目怎么做的**：
- 做了 context_manager（超 20 条触发，保最近 10 条）
- 做了 update_plan（长任务外部记事板）
- 缺子 Agent 分解（单层 ReAct，README 已列为限制）

**⑤ 还能怎么改进**：加 Plan-and-Execute 子 Agent + 引入 Mem0 记忆层（token 省 >90%）。

### 追问链
- 「摘要会不会丢关键信息？」→ 会，这是压缩的代价。所以最近 N 条保留完整，只摘要早期
- 「Context Engineering 和 Prompt Engineering 区别？」→ 前者是系统工程（管整个上下文管道），后者是写技巧（管指令措辞）
- 「Mem0 为什么省 token？」→ 抽取式记忆 + 分层，不全量喂上下文（arXiv:2504.19413）

### 兜底
> "漂移我项目里用摘要 + plan 记事板治，效果还行。Context Engineering 这个新概念我了解不深，但理解是系统化管上下文管道。"

## 难题三：缓存命中（Prompt Caching）

### 一句话答
prompt cache 只认精确前缀匹配，缓存的是已算好的 KV 张量，质量无损只省钱。核心铁律：前缀改 1 个 token 整条缓存失效。

### 展开答（5 层）

**① 是什么**：缓存模型推理的中间状态（KV 张量），下次请求前缀相同就复用，跳过重复计算。

**② 为什么有效**：生成是逐 token 串行的（memory-bandwidth bound），每个 token 的 KV 计算依赖前面所有 token。前缀相同，这部分 KV 一样，不用重算。

**③ 各家政策**（这张表必背）：
| 厂商 | 启用 | 命中折扣 |
|---|---|---|
| Anthropic | 手动 cache_control | 省 90% |
| OpenAI | 全自动 | 省 50% |
| DeepSeek | 全自动 | 省 90% |
| GLM | 隐式自动，无需 cache_control | 省 50-80%（多源不一致） |

**经典命中模式**：[固定系统提示] + [固定工具] + [历史追加] + [当前输入]。前缀越固定越长，命中越好。

**反模式**：时间戳、用户ID、动态检索结果放 prompt 开头——杀缓存。

**④ 你的项目怎么做的**（这是你最强的点）：
- **原来**：时间戳每轮填进 SYSTEM_PROMPT，前缀漂移，缓存永远 miss。
- **我做的**：时间戳移出 SYSTEM_PROMPT 走 config 侧通道，agent_node 临时拼到对话末尾；Anthropic 加 cache_control 标记。GLM 预计省 50-80%，Claude 省 90%。

**⑤ 还能怎么改进**：把动态记忆/RAG 也从系统提示移到末尾（现在还在 system 里）；监控 cache hit rate 加 trace 属性。

### 追问链
- **「为什么前缀匹配是铁律？」→ KV cache 是按 token 位置存的，前缀改一个 token，后面所有位置的 KV 都得重算（详见 [CS 挂钩表](03-考点地图与CS挂钩表.md) 的 KV cache 条）
- 「KV cache 是什么？」→ Transformer attention 里每层每头对每个 token 算的 Key/Value 投影，推理时存下来避免重算（[CS 挂钩表](03-考点地图与CS挂钩表.md)）
- 「语义缓存和 prompt cache 区别？」→ prompt cache 是精确前缀（KV 张量复用，质量无损）；语义缓存是 embedding 相似度（返回旧答案，有时效风险，只适合 FAQ）
- 「GLM 为什么命中率比 Claude 低？」→ 第三方实测 GLM ~53% vs Claude ~91%，GLM 的 cache 实现偏弱（待核实，单一来源）

### 兜底
> "各家政策我背了表。KV cache 的张量级细节我没有深挖到能默写的程度，但理解是推理中间状态复用。"
