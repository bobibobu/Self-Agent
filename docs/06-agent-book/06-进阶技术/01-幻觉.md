# 第 1 章：幻觉（Hallucination）—— 怎么让 Agent 不胡说

> 幻觉是 LLM 的"原罪"——OpenAI 2025 论文定性它是"预训练的固有副产物"。这章讲业界怎么治，本项目差在哪。

---

## 1.1 幻觉是什么

LLM 生成**看似合理但错误/编造**的内容。在 Agent 场景特别危险：

- **事实幻觉**：编造不存在的 API、函数、文件路径
- **工具幻觉**：调用不存在的工具名、编造参数（GPT-4 仍会犯）
- **格式幻觉**：输出畸形的 JSON、错误的代码

⚠️ **一个反直觉发现**（arXiv:2510.22977, 2025）：**增强推理能力反而会放大 tool hallucination**——模型越"会想"，越容易自信地编造一个不存在的函数。这是个反向 trade-off。

---

## 1.2 业界怎么治：按性价比排序

### 必做（baseline）

#### ① RAG（检索增强生成）

**原理**：检索相关文档塞进 prompt，让回答基于文档，而非自由生成。

**为什么必做**：仍是 2026 主力 baseline。学术数据：Self-reflective RAG 把幻觉率降到 **5.8%**（Wolłk, MDPI Electronics 2025）。

**2025 演进**（不只是 naive RAG 了）：

| 变体 | 一句话 | 效果 |
|---|---|---|
| **Naive RAG** | 检索→塞 prompt | baseline，本项目用的 |
| **HyDE** | 先生成假设答案再去检索 | 弥合 query 与文档语义鸿沟 |
| **CRAG（Corrective RAG）** | 检索后加"评估器"打分，低分触发 web 搜索兜底 | 生产常见，鲁棒性强 |
| **Self-RAG** | LLM 自评检索质量，反思 token 决定是否重检 | 学术幻觉降至 5.8% |
| **GraphRAG**（微软） | 文档建知识图谱，图遍历多跳推理 | 复杂关系推理强，建图成本高 |
| **Contextual Retrieval**（Anthropic） | chunk 先用 LLM 加上下文标注 | 检索失败率降 67% |

#### ② 函数调用 grounding

**原理**：把 LLM 锚定到真实数据源，让答案必须来自工具返回。

**为什么必做**：OpenAI 2025 论文明确——外部 grounding 是**必需而非可选**。但注意它**引入了新问题**：工具名/参数幻觉。

#### ③ 结构化输出约束

**原理**：用 JSON Schema / Pydantic 强制输出格式。

**工具**：Outlines、Guidance（微软，2025 评测 per-token 延迟最低）、Instructor、各家原生 Structured Output（OpenAI/Anthropic/Google 都内置）。

⚠️ **关键认知**：**结构合法 ≠ 内容正确**。"一个语法合法的 JSON 仍可能含编造的 order_id"。它治**格式幻觉**，不治**内容幻觉**。别把它当银弹。

### 进阶（按需）

#### ④ Citation / 引用强制

**原理**：强制 LLM 输出时必须标注来源段落，无来源不准说。

**关键**：**Anthropic Citations API**（2025.01）是 Claude 独家原生，号称 RAG 准确率 +15%。其他家靠 prompt 模拟（"必须引用[X]"）。

#### ⑤ CoVe（Chain-of-Verification）/ 反思验证

**原理**：生成答案 → LLM 自己生成验证问题 → 独立回答 → 用验证结果修正（Meta 2023）。4 步流程，token 成本高。

### 高可靠场景

#### ⑥ 多 Agent critic 互验（LLM-as-judge → Agent-as-judge）

**原理**：一个 Agent 生成，另一个专门挑错。

**2025 演进**：从 LLM-as-judge 升级到 **Agent-as-a-judge**（arXiv:2508.02994，judge 自带工具和多步推理）。

⚠️ **实战共识**（Reddit r/LLMDevs）：单个 judge 有偏见/同源错误，**建议跨厂商交叉验证**（用 GLM 生成、用 Qwen 当 judge）。

## 1.3 和 Self-Agent 对比

本项目在幻觉上**几乎是裸奔**：

| 维度 | 业界做法 | 本项目 |
|---|---|---|
| RAG | ✅ naive RAG（`app/rag/`） | ⚠️ **无 CRAG 兜底、无 contextual retrieval、无 HyDE** |
| Grounding | ✅ function calling | ⚠️ **没有强制"答案必须来自工具"** |
| 结构化输出 | ⚠️ 工具参数有 schema | ❌ **agent 最终回复是裸文本，无结构化契约** |
| Citation | ✅ 业界有 | ❌ **完全没有** |
| 自校验/critic | ✅ 业界有 | ❌ **完全没有**（Hermes 反思是优化提示词，不校验事实） |

### 优缺点

- **本项目优点**：简单（省 token、低延迟、少一次 LLM 调用）
- **本项目缺点**：在"答错就出事"的场景（法律/医疗/代码）风险高。Agent 改坏代码、编造不存在的 API，没有兜底

---

## 1.4 给本项目的改造建议

| 建议 | 优先级 | 难度 | 收益 |
|---|---|---|---|
| **RAG 加 CRAG 兜底**（检索评估器，低分触发 web 搜索） | ★★★ | 中 | RAG 鲁棒性 |
| **结构化输出契约**（关键 agent 输出用 Pydantic 强制） | ★★★ | 低 | 杜绝格式幻觉 |
| **Citation prompt 模拟**（"必须引用来源编号"） | ★★ | 低 | 可追溯 |
| **跨模型 critic**（GLM 生成、Qwen 校验） | ★ | 高 | 高可靠场景 |
