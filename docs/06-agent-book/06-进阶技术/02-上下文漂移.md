# 第 2 章：上下文漂移（Context Drift）—— 怎么让 Agent 不失焦

> 这是**本项目做得最好的一块**，方向完全正确。这章讲业界全貌 + 一个 2025 新概念（Context Engineering）。

---

## 2.1 上下文漂移是什么

长对话/长任务中，agent 逐渐**忘记最初目标**、被中间信息带偏、或反复做同一件事。表现：

- 第 7、8 步开始偏离最初任务
- 重复执行已完成的步骤
- 被无关的工具结果带跑

根因：LLM 是"看完所有历史再决定"，历史越长，关键信号越被稀释。

---

## 2.2 业界怎么治

### ① 上下文压缩 / 摘要（baseline，人人都做）

**原理**：对话过长时，把早期历史压缩成摘要，腾出 context window。

**优缺点**：+ 简单；− **压缩即丢信息**，关键细节可能在摘要中丢失。

### ② 分层记忆（Memory Management）

| 方案 | 原理 | 优缺点 |
|---|---|---|
| **LangGraph Store** | 跨会话长期记忆，按 namespace 组织，支持语义检索 | + 官方原生；− 需配后端 |
| **Mem0** | 通用记忆层，按 user/agent/session 三级，2025 加 graph memory | + **token 省 >90%、p95 延迟更低**（arXiv:2504.19413）；− 需独立部署 |
| **Letta（前 MemGPT）** | 记忆当 OS 管：context=内存，archival=磁盘，agent 自管 | + 理论优雅；− 学习曲线陡 |

### ③ 任务计划 / 外部记事板

**原理**：把待办/进度写到外部结构（文件/DB/plan 状态），每轮只读相关部分，避免全量历史污染。

**为什么有效**：给 agent 一块"外部记忆"，不依赖它"记住"，而是每轮都能读到"全局要做什么、做到哪了"。

### ④ 子 Agent / 任务分解（Plan-and-Execute）

**原理**：先规划成结构化步骤，再分步执行；或拆给专门子 Agent。

**代表**：**Aider Architect/Editor**（Architect 解题、Editor 改代码，分离"推理"与"格式敏感生成"）；LangChain Plan-and-Execute agents（3 种模式）。

**共识**："Use Plan-and-Execute when reliability matters"——可靠性要求高时用它。

### ⑤ ★ Context Engineering（2025 新概念，重要）

这是 Karpathy 背书、LangChain 系统化的新词：

> **不是写好 prompt（prompt engineering），而是系统工程地为 LLM 准备合适的上下文**：什么信息进、什么信息出、以什么格式、何时压缩、何时检索。

LangChain 总结了上下文的 **4 种失效模式**：

| 失效模式 | 是什么 | 本项目踩了吗 |
|---|---|---|
| **context poisoning** | 无关/错误信息混入 | ⚠️ RAG 检索到的不相关内容会污染 |
| **context poverty** | 该有的信息没有 | ⚠️ 检索 top-3 不够时 |
| **context distraction** | 信息太多，关键信号被稀释 | ⚠️ 长对话 |
| **context conflict** | 矛盾信息 | — |

2026 调研：**82% 的 IT/数据负责人认为 prompt engineering 单独已不够用**，context engineering 成了 agent 设计的元话语。

### ⑥ Agentic Context Window 管理

**代表**：Letta memory blocks（persona/human/archival/recall 四块）、LangGraph long-term memory、Mem0 graph memory。

**原理**：把有限 context window 当稀缺资源工程化管理，分块、分层、按需加载。

## 2.3 和 Self-Agent 对比

本项目上下文漂移处理是三大难题里**最扎实的**：

| 技术 | 本项目 | 评价 |
|---|---|---|
| 滑动窗口摘要 | ✅ `context_manager.py`（超 20 条触发，保最近 10 条） | 方向对 |
| 外部记事板 | ✅ `update_plan`（长任务外部记忆） | 方向对 |
| 分层记忆 | ✅ 有 Store 长期记忆 | ⚠️ 不如 Mem0 精细 |
| 子 Agent / Plan-and-Execute | ⚠️ 有 plan 但**单层 ReAct**，无子 Agent 分解 | README 已列为限制 |
| Context Engineering | ⚠️ 实践了（动态记忆+RAG 拼提示）但没系统化 | 缺方法论 |
| Agentic context window 管理 | ❌ 没有 Letta 那种分块 | 缺 |

### 一个值得注意的副作用

本项目"动态记忆+RAG 拼系统提示"是 context engineering 的实践，**但恰好是破坏 prompt caching 的元凶**（见第 3 章）。这是准确性与缓存的本质张力。

## 2.4 给本项目的改造建议

| 建议 | 优先级 | 难度 | 收益 |
|---|---|---|---|
| **加 Plan-and-Execute 子 Agent**（复杂任务拆解） | ★★ | 高 | 长任务可靠性（解决 README 列的"无子 Agent"限制） |
| **引入 Mem0 做记忆层**（替代简化 Store） | ★★ | 中 | token 省 >90%、p95 延迟降 |
| **系统化 Context Engineering**（4 种失效模式对照排查） | ★ | 中 | 方法论 |
