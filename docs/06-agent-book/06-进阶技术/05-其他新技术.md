## 5.2 Reranking（重排）—— 几乎是免费收益

### 原理
两阶段检索：
1. **粗召**：bi-encoder/向量库快速取 Top-K（如 K=100）
2. **精排**：cross-encoder 对这 K 个精细打分重排，取最终 Top-N

### 为什么重要
向量检索召回率高但**精度不足**（尤其代码/长文档）。cross-encoder 能把精度显著提升（常 +10-20% nDCG）。

### 工具
- **开源首选**：bge-reranker、jina-reranker-v2（v2 针对 agentic/code 优化）
- **商用**：Cohere Rerank

### 给本项目
**强烈建议**。本项目若做代码/文档 RAG，加一层 bge-reranker 几乎是"免费"收益，和 MCP 检索类工具天然契合。改动小（检索后加一道重排），收益大。

---

## 5.3 Evals（评测）—— Agent 质量保证

### 为什么 Agent 需要 Evals
Agent 输出**非确定**，传统单测（输入→精确输出比对）失效。需要：
- **LLM-as-judge**：用另一个 LLM 打分
- **规则断言**：检查输出是否含某关键信息、是否合法 JSON
- **回归测试集**：跑在 CI 防止改 prompt 后质量倒退

### 工具生态
| 工具 | 定位 |
|---|---|
| **Promptfoo** | CI/安全测试强 |
| **DeepEval** | 开源指标全（RAG/agentic） |
| **Langfuse Evals** | 生产 trace + 评测闭环 |
| **Pydantic Evals** | 结构化/多 agent 工作流 |

### 给本项目
**必须**。本项目有 Hermes 反思，但反思只是 LLM 自评分，**没有 eval set 把关**（README 已列为限制）。建议 Promptfoo（CI 回归）+ Langfuse（线上 trace→eval 闭环）组合，Hermes 反思可用 eval 做奖励信号。

## 5.4 Prompt Optimization（自动优化提示词）—— DSPy

### 原理
把 prompt 当**可训练参数**，给定训练集+指标，自动搜索最优 instruction/few-shot。把玄学 prompt 工程变成可度量工程。

### 三大流派
- **DSPy**（最成熟）：compiler/optimizer 范式，GEPA/MIPRO 等优化器
- **TextGrad**（Stanford）：文本反向传播，PyTorch 风格，用 LLM 反馈当梯度
- **Promptflow**：⚠️ 注意歧义——学术框架 vs 微软 Azure Prompt Flow（2027.4 退役）

### 给本项目
**强烈建议，且和 Hermes 互补**。本项目 Hermes 反思是**事后修正**（运行时改提示词）；DSPy 是**事前优化**（离线搜最优 prompt）。两者互补——可先用 DSPy 优化子任务 signature，再用 Hermes 做运行时纠错。

## 5.5 Computer Use / Browser Use —— 2025 最大新能力

### 是什么
Agent 直接"看屏幕/操作浏览器"，把 GUI 当工具调用。突破"只能调 API"的限制。

### 现状
- **闭源**：Anthropic Computer Use（2024.10，控制桌面）、OpenAI Operator→2025.7 并入 ChatGPT Agent（控制浏览器）
- **开源**：**browser-use**（~97k star，自称 #1 开源浏览器自动化）

### 给本项目
**值得（作 MCP 工具接入）**。browser-use 可作为 MCP/工具层一环，让 agent 具备"看网页、填表单、E2E 测试"能力。和本项目 MCP 架构天然契合——本项目本就有 MCP client，加一个 browser MCP server 即可。

## 5.7 Tokenizer / 计费优化 —— 基本功但重要

### 原理
用 tiktoken/分词器在调用前**精确计 token**，结合 context-aware 截断（按相关度裁剪历史）控成本。

### 为什么对 Agent 重要
多 agent 循环中 token 成本失控——supervisor + subagent 每个 prompt 都重发。Mem0 等提出"3-4x 降本 playbook"，核心是**记忆分层 + 智能截断**而非全量喂上下文。

### 给本项目
**必须**。本项目 LangGraph 多节点，每节点 system prompt + 状态重复传输是大成本源。建议：
- tiktoken 预估（本项目 context_manager 只数消息条数，不数 token，全书第 3 章已指出）
- 按节点相关度裁剪 state
- 记忆外置（见第 2 章上下文漂移）

## 5.8 Guardrails（安全护栏）—— 2025 安全热点

### 是什么
在 LLM 输入/输出加**可编程护栏**：
- **input rail**：拦 prompt injection
- **output rail**：拦有害内容
- **dialog rail**：控对话流程

### 工具
| 工具 | 开源？ | 状态 |
|---|---|---|
| **NeMo Guardrails**（NVIDIA） | ✅ | 主流，0% 注入绕过但 16% 误杀率 |
| **Llama Guard 3 / NemoGuard-8B** | ✅ | 二分类模型（Llama Guard 4 待核实） |
| **Rebuff**（Protect AI） | ✅ | ⚠️ 2025 被收购后 archived，维护停滞 |
| **Lakera Guard** | ❌ 商用 | 0% ASR，生产级 |

### 共识
无单一模型够用，需**分层**（NeMo 框架 + Guard 模型 + 业务规则）。

### 给本项目
**建议（按风险等级）**。本项目若处理外部输入（browser-use 抓网页、MCP 外部数据、RAG 文档），至少加 NeMo input rail 防 prompt injection；纯内部编码场景可暂缓。和第 1 章幻觉的 grounding 互补。

## 5.9 只在自托管时有用的技术

### Speculative Decoding（推测解码）
小"草稿模型"快速预生成，大模型并行验证，**数学上无损**。vLLM 原生支持 Eagle 3。加速比 1.4-4x。

**本项目用云端 GLM API，无法控制解码**。只有未来自托管（vLLM/SGLang）时才用得上。

### Streaming + interruption 工程优化
推理引擎针对 agent"流式+工具调用+中断重启"优化 KV cache。**vLLM（PagedAttention）vs SGLang（RadixAttention）** 是双雄，SGLang 对多轮/工具调用据称快 2-3x（待核实）。

同样，**仅自托管时相关**。

---

## 5.10 Mixture-of-Agents (MoA) —— 小众但有场景

### 原理
多层架构：每层多个 proposer LLM 并行生成，下一层 aggregator 聚合。用"弱模型集体"逼近强模型。Together AI 主推（AlpacaEval 2.0 上 65.1% 一度超 GPT-4o）。

### 为什么没成主流
成本和延迟**成倍上升**（N proposer + 1 aggregator × L 层）。2025 后被"单一大模型 + 强 agent"路线盖过。

### 给本项目
**小众借鉴**。仅在"高价值、低频、质量敏感"的子任务（最终答案评审、代码 review）可考虑双层 MoA；主循环不建议。
