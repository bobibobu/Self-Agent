# 第 3 章：缓存命中（Prompt Caching）—— 怎么让 Agent 省钱省延迟

> 这是最技术性、最值得深挖的一章。**也是本项目最大的优化机会——当前用法是反模式。**
> 这章的事实已逐一核实，尤其 GLM（你最关心的）。

---

## 3.1 Prompt Caching 是什么

缓存的是**已算好的 KV 张量**（模型推理的中间状态）。下次请求若前缀相同，直接复用，跳过重复计算。

**质量无损，只省算力/钱/延迟**。

### 核心铁律

> **只认精确前缀匹配（exact prefix match）。前缀改 1 个 token，整条缓存失效。**

OpenAI 官方原话："Cache hits are only possible for **exact prefix matches** within a prompt"。

### 经典命中模式

```
[固定系统提示] + [固定工具定义] + [固定 few-shot] + [历史对话追加] + [当前用户输入]
↑─────────── 这段越固定越长，命中越好 ───────────────↑
```

### 反模式（杀缓存）

- 把**时间戳、用户ID、动态检索结果**放 prompt 开头
- 系统提示每轮内容都变

## 3.3 🔴 GLM Prompt Caching 专题（你最关心的）

### 结论

**GLM 支持 prompt caching，而且是隐式自动的，不用写 `cache_control`。** 来源：智谱官方文档 docs.bigmodel.cn/cn/guide/capabilities/cache。

### 官方原文要点

- 「隐式缓存，智能识别重复的上下文内容，**无需手动配置**」
- 命中规则：「识别与之前请求中**相同或高度相似**的内容」——前缀精确匹配命中率最高，「轻微的格式差异可能影响缓存效果」
- 「缓存有合理时效性，过期后重新计算」（具体 TTL 未公布，待核实）
- 支持模型：GLM-5.2、GLM-5.1、GLM-5 系列；GLM-4.7、GLM-4.6V

### ⚠️ 折扣数字多源不一致（如实标注）

| 来源 | 缓存命中价 | 折扣 |
|---|---|---|
| 官方缓存功能文档 | "标准价格的 50%" | 50% off |
| GLM-4.7 定价页（qianwenai） | ¥0.6/M vs ¥3/M | **80% off（仅 20% 价格）** |
| 积分系数表 | 1.2 vs 4.6 | 约 74% off（26% 价格） |

→ **保守说法**："GLM 支持 prompt caching，缓存命中显著降价，约省 **50-80%**，具体以官方实时定价为准。"

### ⚠️ 实战命中率警示

第三方实测（VibeCafé）：**GLM 平均命中率约 53%，Claude Sonnet 约 91%**。即 GLM 的 cache 实现偏弱，实际节省可能打折扣。此数据为单一第三方实测，样本有限，标待核实。

## 3.4 ⚠️ 本项目为什么命中不了（真实痛点）

本项目系统提示是**每轮动态拼的**（`graph.py:_build_system_prompt_with_context`）：

```
基础人设 + 当前时间（每轮变）
  + Hermes 优化版提示（会变）
  + Skill 提示（可能变）
  + RAG 检索结果（每轮不同）      ← 动态
  + 长期记忆 top-3（每轮不同）     ← 动态
  + 用户画像（会变）
```

**系统提示每轮内容都变 → 前缀不固定 → GLM 的 prompt cache 永远 miss。**

这是**根本性张力**：动态上下文有利于准确性（context engineering），但**破坏缓存**。本项目选了准确性，牺牲了缓存。

而且代码里 `stream_chat` 调用**没传任何 cache 相关参数**，也没 `extra_headers` 处理 cache_control——对 GLM（隐式）无所谓，但切到 Anthropic 时也没用手动标记，白白浪费了 Claude 的 90% 折扣。

## 3.5 怎么改（优化方向）

### 方案①：分层 prompt（最重要）

把"真·固定"部分（角色、工具 schema、few-shot）放最前并**冻结**；动态部分（记忆/RAG）放**最后**：

```
[冻结：角色 + 工具 schema + few-shot]   ← 这段每轮完全一样，能撞缓存
[历史对话追加]
[动态：本轮 RAG/记忆]                    ← 放最后，不影响前缀缓存
```

### 方案②：动态内容移出系统提示

记忆/RAG 改用 Store/文件，每轮只检索**最小集**注入到**末尾**，减少前缀变动。

### 方案③：Anthropic 场景手标 breakpoint

切到 Claude provider 时，用 `cache_control` 把固定段标成 cache（1h TTL），命中率能到 90%+。本项目目前完全没用这个。

### 方案④：GLM 场景

隐式缓存无法手标，**只能靠前缀结构稳定**撞缓存。预期命中率 < Claude（53% vs 91%），别期待太高。

## 3.6 语义缓存（Semantic Cache）—— 另一种思路

**原理**：用 embedding 相似度判断"这个问题问过没有"，相似就返回缓存答案（**不是精确前缀，是语义近似**）。

**代表**：GPTCache（开源主流）、Redis LangCache（命中率 73%）、Portkey、Langfuse cache。

**效果**：FAQ/客服场景命中 40-80%，延迟从 ~850ms 降到 ~120ms（约 7×），成本省 40-70%。

⚠️ **致命风险：语义假阳性**——相似但不等同的问题返回了错误答案。需按领域调阈值。**不适合 agent 的工具调用场景**（工具调用结果时效性强，缓存风险高）。

## 3.7 和 Self-Agent 对比

| 维度 | 业界 | 本项目 |
|---|---|---|
| Prompt Caching | Anthropic 省 90%、GLM 省 50-80% | ❌ **反模式，永远 miss** |
| cache_control 标记 | Anthropic 场景必用 | ❌ 代码里没有 |
| 前缀结构 | 固定前置、动态后置 | ❌ 动态内容混在系统提示 |
| 语义缓存 | FAQ 场景用 | ❌ 没有（agent 场景也不该用） |

### 优缺点

- **本项目优点**：系统提示灵活（每轮都能注入最新记忆/RAG）
- **本项目缺点**：**白白浪费 GLM 的 cache 折扣**，长期成本高、首字延迟高（每次都要重算前缀 KV）

## 3.8 给本项目的改造建议

| 建议 | 优先级 | 难度 | 收益 |
|---|---|---|---|
| **重构 prompt 拼装顺序**（固定前置、动态后置） | ★★★ | 低 | GLM 命中率从 0 提升 |
| **Anthropic provider 加 cache_control** | ★★★ | 低 | Claude 命中率到 90%+，省 90% |
| **时间戳移出系统提示**（放历史末尾或 config） | ★★ | 低 | 减少前缀变动 |
| 监控 cache hit rate（trace 里加属性） | ★ | 低 | 可观测 |
