# 第 6 章：最强开源 Agent 的依赖栈与缺口

> 假设要组装一个"业界最强、完全开源"的编码 Agent（对标 Claude Code/Cursor，但全开源）。
> 这章逐层列出该用什么开源组件，并**明确指出开源还做不到的缺口**。

---

## 6.1 先给结论

**一句话**：开源在**编排、工具协议、沙箱、可观测、安全**层已全面达标 Claude Code/Cursor；真正瓶颈是 **① 底层编码模型能力 ② 一体化代码理解质量 ③ 产品级编辑器体验** 三块。

### 层 5：★ 编码 Agent 专项（开源 vs 闭源核心战场）

#### Claude Code / Cursor 的"代码理解"靠什么？

1. **tree-sitter**：100+ 语言的增量 AST 解析器，**所有现代代码理解的地基**
2. **Aider repo-map（开源经典范式）**：
   - tree-sitter 解析每个文件 → AST → 抽取符号定义/引用为"tags"
   - 构建有向图（文件为节点，依赖为边）
   - **PageRank 类算法**排序，被引用最多的符号优先级最高
   - 按 token 预算（默认 1000 token）裁剪
   - 输出结构化大纲（文件 + 关键符号签名 + 省略号）
3. **Cursor（闭源）的增强**：tree-sitter AST 切块 → embedding → 向量库 + **Merkle tree 增量重索引**（50k 文件 21 秒）
4. **SCIP（Sourcegraph，开源协议）**：Protobuf 格式的语言无关代码索引，含定义/引用/hover 文档，是 LSIF 继任者。比 tree-sitter 多"语义跨引用 + 稳定符号 ID"

#### 开源编码 Agent 现状（2025-2026）

| 项目 | 定位 |
|---|---|
| **OpenHands**（前 OpenDevin） | 开源、模型无关的云编码 agent，**对标 Devin 的头号开源对手**，有 CLI 版 |
| **Aider** | 终端 pair programming，repo-map 是其代码理解核心 |
| **Cline / Roo Code / Kilo Code / OpenCode** | VSCode 系新兴开源 agent |
| **Continue** | ⚠️ 2026 已 **legacy（repo read-only）**，不推荐 |

**新趋势——代码理解 MCP 化**：CodeGraph（tree-sitter→SQLite 图，号称减 70% 工具调用）、jCodeMunch MCP（tree-sitter + SCIP）、CocoIndex、spy-code MCP。**把"代码理解"做成 MCP server 喂给 Claude Code/Cursor 的新玩法**。

#### SWE-bench Verified（编码 agent 黄金评测）

- SOTA 区间约 **93-97%**（闭源 Claude Opus/GPT-5.x 居顶，**待核实** swebench.com）
- **开源/轻量**：mini-SWE-agent 用 100 行 Python 拿 74%——**说明 agent 框架已不是瓶颈，模型能力是**
- SWE-bench Verified 趋于饱和，社区转向 **SWE-bench Pro**（SOTA 仅 ~58-69%）

### 层 6：沙箱/执行层

| 组件 | 类型 | 定位 |
|---|---|---|
| **E2B** | 开源（OSS 核心）+ 托管 | **市场领先**，Firecracker microVM，专为 agent 代码执行 |
| **Daytona** | 开源 | 2025 转型 AI agent 基础设施，支持持久化 |
| **Modal** | 托管（非开源） | 通用 serverless |

**推荐**：自托管用 **E2B OSS（Firecracker）**；轻量本地用 bubblewrap/Landlock（本项目已用）。

### 层 7：可观测/评测

- **Langfuse**：**开源首选**，原生 OpenTelemetry + GenAI 语义约定，trace/prompt/eval 一体

- **Arize Phoenix / LangWatch（Apache-2.0）/ OpenObserve / MLflow**：开源备选
- **评测**：**SWE-bench**（代码 agent 标准）+ Promptfoo（CI）+ Inspected

## 6.4 ★ 哪些能力开源还做不到？（明确缺口清单）

### 缺口①：底层编码模型能力（最大缺口）

SWE-bench SOTA 区 93-97% 由闭源 Claude/GPT 占据；开源最佳模型仍有差距。**这不是框架能补的，是模型层差距**。

### 缺口②：代码理解质量（核心缺口）

- 开源有 tree-sitter + PageRank（Aider），但缺 **Cursor 级别的 Merkle tree 增量重索引 + 语义 embedding 联合检索**的**开箱即用一体化产品**
- SCIP 语义索引虽开源，但**多语言 indexer 覆盖和质量不如 Sourcegraph 商用版**
- "上下文化的代码索引"（context-aware，随当前任务动态调整）开源方案零散（CodeGraph/CocoIndex 都是 MCP 实验项目，未成熟）

### 缺口③：长上下文管理

开源模型长上下文（Llama 4 10M 标称）实测有效利用度、长程代码推理弱于 Claude；开源记忆框架（Mem0/Letta）无单一赢家。

### 缺口④：流式工具调用稳定性

vLLM/SGLang 工具调用原生支持，但**多 agent interleaved tool calling 的显存调度/中断恢复**仍是研究问题；LayerScale 等新引擎声称解决但生态未成熟。

### 缺口⑤：端到端产品打磨

闭源有 IDE 深度集成、diff 预览、撤销、多文件原子编辑等产品体验；开源 OpenHands/Aider 偏 CLI/云，**VSCode 级编辑器内集成体验落后于 Cursor**。

### 缺口⑥：统一评测闭环

SWE-bench 评测开源可用，但"线上 trace → 自动 eval → 回归"的开源一体化产品仍弱于 LangSmith 商用版。

## 6.5 ★ Self-Agent 离"最强"还差哪些开源组件？

| 层 | 现状 | 缺口（需补的开源组件） |
|---|---|---|
| 推理 | GLM API | 本地化时补 **SGLang**（多轮/工具调用最优） |
| 编排 | LangGraph ✅ | 基本够，可加 **Mem0/Letta** 记忆层 |
| 工具 | MCP ✅ | 加 **playwright-mcp + browser-use**（GUI 能力） |
| **代码理解** | **缺** | **加 Aider repo-map 机制 或 CodeGraph MCP + tree-sitter + SCIP indexer**（最关键缺口） |
| RAG | 待补 | **Qdrant + BGE-M3 + bge-reranker**（代码检索补 Nomic Embed Code） |
| **沙箱** | **缺**（只有 bubblewrap/Landlock） | **E2B OSS（Firecracker）** 执行 agent 生成代码 |
| 可观测 | OTel ✅（自研轻量） | **Langfuse**（开源，OTel 原生，更强） |
| 评测 | 待补 | **Promptfoo（CI）+ SWE-bench 子集** |
| 安全 | 工具层（审批/沙箱） | **NeMo Guardrails**（若处理外部输入） |
| 提示优化 | Hermes 反思 ✅ | 叠加 **DSPy**（事前优化，与 Hermes 互补） |

**最关键的 3 个缺口**：
1. **代码理解层**（repo-map + SCIP）—— 让 agent 在大仓库精准导航
2. **沙箱执行**（E2B）—— 比本项目 bubblewrap/Landlock 更强的隔离（microVM）
3. **本地编码模型能力**——等开源模型追平，或自托管 DeepSeek-V3/Qwen3
