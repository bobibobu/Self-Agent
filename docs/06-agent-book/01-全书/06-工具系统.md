## 6.1 工具调用的完整流程（复习 + 加深）

第 1 章讲过基本流程，这里用本项目的真实代码加细。

### 第 1 步：声明工具，给 LLM 看清单

在 agent_node 里：

```python
tools = configurable.get("tools", [])
request = build_chat_request(messages, tools)
```

`build_chat_request`（`nodes/bridge.py:69`）把工具转成 LLM 看得懂的 schema：

```python
def build_tool_definitions(tools):
    for t in tools:
        name = getattr(t, "name", str(t))
        description = getattr(t, "description", "")
        args_schema = getattr(t, "args_schema", None)
        schema = args_schema.model_json_schema()  # ← Pydantic 模型变 JSON Schema
        defs.append(ToolDefinition(name=name, description=description, parameters=schema))
```

**关键魔法**：工具就是一个 Python 函数 + Pydantic 参数模型，`model_json_schema()` 自动把它转成 JSON Schema。你不用手写 schema。

### 第 2 步：LLM 输出工具调用

大模型看到清单后，决定调用时输出：

```json
{"id": "call_abc", "name": "read_file", "args": {"path": "main.py"}}
```

### 第 3 步：tools 节点执行

`nodes/tools_node.py` 的 `tools_node`：

```python
async def tools_node(state, config, writer):
    last_msg = state["messages"][-1]
    tool_calls = getattr(last_msg, "tool_calls", None) or []
    # 并发执行所有 tool_calls
    results = await asyncio.gather(*(_run_one(c, writer, limit) for c in tool_calls))
    messages = [msg for msg, _ in results]
    updates = {}
    for _, upd in results:
        updates.update(upd)
    return {"messages": messages, **updates}
```

并发执行——3 个各 2 秒的工具总共约 2 秒，不是 6 秒。顺序与 tool_calls 一致（OpenAI/Anthropic 要求每个 tool_call_id 有且仅有一条对应结果）。

### 第 4 步：结果回填

工具结果作为 ToolMessage 追加到 messages，回到 agent 节点，LLM 看到结果决定下一步。

## 6.2 一个工具长什么样：@tool 装饰器

看一个真实的只读工具（`app/agent/tools/files.py:52`）：

```python
@tool
async def read_file(path: str, start_line: int = 1, end_line: int = 0) -> str:
    """读取工作区内某个文本文件的内容，带行号。

    Args:
        path: 相对工作区根目录的文件路径，例如 "app/main.py"
        start_line: 起始行号（从 1 开始），默认 1
        end_line: 结束行号（含）。0 表示读到文件末尾
    """
    ws = get_workspace()
    try:
        target = ws.resolve(path)   # ← 工作区禁闭检查
    except WorkspaceError as e:
        return _err(str(e))
    if ws.is_sensitive(target):
        return _err(f"拒绝读取敏感文件：{ws.relative(target)}")
    if not target.exists():
        return _err(f"文件不存在：{path}")
    # ... 真的读文件 ...
    return _read_text(target, limit)
```

**三件事自动发生**：
1. **函数名 → 工具名**：`read_file`
2. **docstring → 工具描述**：完整 docstring 给 LLM 看，让它知道这工具干嘛、参数啥意思
3. **类型注解 + Pydantic → JSON Schema**：`path: str`、`start_line: int = 1` 自动变成 schema

所以你写一个工具，**就是写一个带类型注解和好 docstring 的 Python 函数**。`@tool` 装饰器把它包装成 LangChain `BaseTool`。

## 6.3 ★ 风险分级：决定要不要问你

这是编码 Agent 安全设计的核心。工具按「出错的后果可不可逆」分三档（`app/agent/registry.py`）：

```python
class ToolRisk(StrEnum):
    READ = "read"    # 读文件、搜索、算数 —— 错了重来即可
    WRITE = "write"  # 写/改/删文件 —— 改变工作区，可逆但要人知情
    EXEC = "exec"    # 执行命令、访问网络 —— 后果不可预测且可能不可逆

DEFAULT_RISK = ToolRisk.EXEC  # ← 未知工具默认最高风险
```

**分级依据不是「操作复不复杂」，是「出错的后果可不可逆」**。`calculator` 算错重算即可，所以是 READ；`delete_file` 删了要找回来，所以是 WRITE；`run_command` 可能做任何事，所以是 EXEC。

### 为什么要 DEFAULT_RISK = EXEC

新工具（尤其 MCP 发现来的第三方工具）接进来时**没声明风险**。如果默认放行，一个可能删库的第三方工具就默默被自动执行了。**故意的保守默认**：宁可多问用户一次，也不能默默放行。

内置工具的等级在 `registry.py` 启动时补齐，避免连 calculator 都要弹审批。

### 风险等级怎么传

两种方式：
1. **内置工具**：`tools/__init__.py` 的 `TOOL_RISKS` 字典
2. **任何工具**：`@tool(metadata={"risk": "read"})`，`_risk_from_metadata()` 读取

## 6.4 ★ 审批策略：四档模式

`nodes/tools_node.py` 的 `needs_approval()` 按 `TOOL_APPROVAL_MODE` 判断：

| 模式 | 行为 | 用途 |
|---|---|---|
| `gated`（默认） | WRITE 和 EXEC 要问 | 本地正常开发 |
| `auto` | 全部放行 | **仅限沙箱/CI** |
| `strict` | 全部都问 | 极度谨慎 |
| `readonly` | 只读放行，其余**直接拒绝**（不问） | 只想让它看不能改 |

还有个 `TOOL_AUTO_APPROVE=工具名1,工具名2` 白名单，列出的工具永不询问。

**审批结果解析的 fail-closed 设计**（`_parse_decision`）：

```python
def _parse_decision(decision):
    if isinstance(decision, bool):
        return decision, ...
    if isinstance(decision, str):
        ok = decision.strip().lower() in {"approve", "yes", ...}
        return ok, ...
    if isinstance(decision, dict):
        ok = bool(decision.get("approved"))
        return ok, ...
    return False, f"无法识别的审批结果，按拒绝处理"  # ← 识别不了就拒绝
```

**识别不了的审批结果一律按拒绝处理**——否则一个格式不对的回包就会变成静默放行。这是安全设计的关键：审批环节失效时默认必须是不执行。

## 6.5 ★ 工具注册表：单一真相来源

`app/agent/registry.py` 是所有工具的汇聚点。三类来源全汇到这里：

```
内置工具（@tool 定义的 files/shell/plan）
   ↓
MCP 工具（运行时从外部 MCP server 发现的 BaseTool）
   ↓ TOOL_MAP + register_tool + refresh_from_mcp
Skill 工具（Skill 系统注册的）
   ↓
   ┌──────────────────────────┐
   │  app.agent.registry      │ ← 单一真相来源
   │  _registry: {name: tool} │
   │  _risks: {name: ToolRisk}│
   └──────────────────────────┘
       ↓ get_all_tools()       ↓ get_tool(name)
   LLM 看到的工具清单       tools_node 执行时按名查
```

**价值**：保证「LLM 看到的工具声明」和「tools_node 执行时的映射」一致。不会出现 LLM 以为有某工具但执行时找不到，或反过来。

`get_all_tools()` 给 LLM 看的清单，`get_tool(name)` 执行时按名查找。

### MCP 工具怎么进来

`app/main.py` lifespan 里：

```python
await mcp_client_manager.connect()
if mcp_client_manager.tools:
    n = refresh_from_mcp(mcp_client_manager.tools)
```

`refresh_from_mcp` 把 MCP 发现的工具合并进注册表（重名保留内置版本）。从此这些 MCP 工具和内置工具走**完全相同**的执行路径——这是注册表统一的价值。

## 6.6 工具执行的完整流水线

`tools_node._run_one()`（`nodes/tools_node.py:89`）每个工具调用走这条流水线：

```
1. 策略检查      readonly 模式下，写和执行直接拒绝（不打扰用户）
2. 审批检查      needs_approval() 判定
      ├─ 需要 → interrupt() 挂起整张图 ⏸
      │        用户决策后从原地继续
      │        识别不了的决策 → 按拒绝
      └─ 不需要 → 继续
3. 找到工具      get_tool(name) 从注册表查
      └─ 找不到 → 返回"错误：未知工具"，span 标红
4. 执行          path 检查 → 沙箱包装 → 真的跑
      └─ 异常 → 错误交回模型（不中断循环），span 标红
5. 截断          结果太长截断到 TOOL_RESULT_MAX_CHARS
6. 返回          ToolMessage 塞回状态
```

**两个关键设计**：

1. **工具失败不中断 ReAct 循环**——错误作为 ToolMessage 交回模型，它可以换个参数重试。但 span 要标红：对模型是「可恢复」，对排查的人是「这里出事了」。
2. **工具可以返回 StateUpdate**——既给模型一段文本，又更新图状态（比如 `update_plan` 维护任务计划）。`tools_node` 认得这个类型，不用按工具名特判。

## 6.7 内置工具有哪些

`app/agent/tools/files.py`（文件工具）+ `shell.py`（Shell）+ `plan.py`（计划）+ `app/agent/tools/__init__.py` 里的玩具工具（calculator/get_current_time/get_weather）。

文件工具一览：

| 工具 | 风险 | 说明 |
|---|---|---|
| `read_file` | READ | 带行号读取，支持行范围，自动跳过敏感文件 |
| `list_dir` | READ | 列目录，自动跳过 .git/node_modules |
| `glob_files` | READ | 通配符查找 |
| `grep_files` | READ | 字面量内容搜索，跳过二进制和敏感文件 |
| `write_file` | WRITE | 覆盖写入，父目录自动创建 |
| `edit_file` | WRITE | 精确文本替换；匹配多处时**拒绝而非猜测** |
| `delete_file` | WRITE | 只删单个文件，拒绝删目录 |
| `run_command` | EXEC | 不经 shell 解释器，超时杀进程组（详见第 8、9 章） |
| `update_plan` | READ | 维护任务计划（第 9 章） |

**edit_file 匹配多处时拒绝**——这是个重要的安全细节。猜测改哪个会出错，宁可让模型看到「匹配到 N 处，请提供更精确的上下文」自己纠正。

## 6.8 工具结果的截断

第 3 章提过：工具结果写进 messages 前会被 `_truncate()` 截断到 `TOOL_RESULT_MAX_CHARS`。

这是为什么 tools_node 流水线里有「截断」这一步。截断后还会单独推一个 `tool_result` 事件给前端（截断到 500 字符），让用户看到工具干了啥（但不污染 LLM 的上下文）。

## 6.9 外部世界怎么做

| 项目 | 工具机制 |
|---|---|
| **OpenAI function calling**（2023.06） | 单次调用语义，模型输出结构化 JSON |

| **Cursor** | 内置工具 + MCP |

**演进脉络**：function calling 解决「单次调用」，MCP 解决「M×N 集成爆炸」。详见拆解③。

## 6.10 面试一句话

> **Q：工具调用是怎么发生的？**
> A：大模型不调用工具，它只输出结构化 JSON 描述「想调用什么」。程序解析这个 JSON，真的去执行，结果作为 ToolMessage 回填给模型。本项目用 @tool 装饰器把 Python 函数 + Pydantic 参数自动转成 LLM 看得懂的 schema。

> **Q：工具风险分级依据是什么？**
> A：「出错后果可不可逆」，不是操作复杂度。READ 错了重来，WRITE 改工作区要人知情，EXEC 后果不可预测。未知工具默认 EXEC——保守默认，宁可多问。
