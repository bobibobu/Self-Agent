# 第 3 章：状态的真相

> 这章专门回答你的核心疑问：
> - 状态保存的时候，**到底存的是什么**？
> - 存的 message 是**提炼后的摘要，还是一字不差的原文**？
> - 系统提示词存不存？每轮都重新拼吗？
> - agent 怎么「记住」上一句话的？
> - 工具调用结果那么长，会不会撑爆上下文？
>
> 读完这章，上面每个问题你都能精确回答。

---

## 3.1 先破除一个迷思：「LLM 有记忆」

很多人以为大模型能记住对话。**没有。** 大模型是一个纯函数：

```
f(所有历史消息 + 当前问题) → 回答
```

它每次都是**从零开始**，看到你塞给它的全部消息，然后输出。所谓「它记得上一句」，是因为**你的程序把上一句也塞进去了**。

所以「Agent 的记忆」这件事，本质是：**你的程序怎么保管历史消息、什么时候塞给 LLM、塞哪些**。

LangGraph 的 **State + Checkpointer** 就是干这个的。下面我们把它的每一个细节拆开。

---

## 3.2 State 到底是什么：两个字段

在 `app/agent/state.py` 里，State 的定义只有这么点：

```python
class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    plan: NotRequired[Annotated[list[dict], replace_plan]]
```

翻译成人话：**State 就是两样东西的集合**：

| 字段 | 装的是什么 | 形态 |
|---|---|---|
| `messages` | 整段对话历史 | 一个消息列表 |
| `plan` | 任务计划 | 一个步骤列表 |

就这两样。没有别的。所有「记忆」「上下文」都装在 `messages` 里。

---

## 3.3 ★ messages 里的「一条消息」长什么样（原文，不是摘要）

这是你最关心的：**存的是原文还是提炼后的摘要？**

**答：原文，一字不差。** 而且是**结构化的对象**，不是一段大文本。

`messages` 是一个列表，每一条是一个 **LangChain 消息对象**。有四种角色：

### ① HumanMessage —— 用户说的话

```python
HumanMessage(content="读一下 main.py，然后加个注释")
```

`content` 就是你敲的那句话，**原文**，不做任何提炼。

### ② AIMessage —— 大模型的回复（可能带工具调用）

```python
AIMessage(
    content="好的，我先读一下 main.py",
    tool_calls=[{"id": "call_1", "name": "read_file", "args": {"path": "main.py"}}]
)
```

注意它有**两部分**：
- `content`：大模型说的「人话」（可能为空，如果它只决定调工具不说话）
- `tool_calls`：它想调用的工具（**完整保留**，因为下一轮要靠它回填结果）

`additional_kwargs` 里还会塞 `usage`（token 用量）、`model`、`provider` 等元信息（供日志统计用）。

### ③ ToolMessage —— 工具执行的结果

```python
ToolMessage(
    content="1  import os\n2  ...\n3  def main(): ...",  # 文件内容，原文
    tool_call_id="call_1",   # 对应哪个 tool_call（靠这个 ID 配对）
    name="read_file",
)
```

`content` 是工具的真实输出，**原文**（但会被截断，见 3.6）。`tool_call_id` 用来告诉大模型「这个结果对应你刚才的第几号调用」——因为一次可能并发调多个工具。

### ④ SystemMessage —— 系统提示词

```python
SystemMessage(content="你是 Self-Agent，工作原则是……")
# 注意：当前时间已移出系统提示（见 3.5 的 prompt 缓存设计），
# 改走 config 通道由 agent_node 拼到对话末尾，避免破坏缓存前缀
```

**这个最特殊，见 3.5。**

### 一段完整对话历史的真实样子

跟着「读 main.py 加注释」走一遍，`messages` 列表大概长这样：

```python
[
    HumanMessage("读一下 main.py，然后加个注释"),
    AIMessage(content="", tool_calls=[{id:"c1", name:"read_file", args:{path:"main.py"}}]),
    ToolMessage(content="<main.py 全文>", tool_call_id:"c1", name:"read_file"),
    AIMessage(content="我读到了，现在加注释", tool_calls=[{id:"c2", name:"edit_file", args:{...}}]),
    # ← 这里触发审批，图挂起
    # ... 用户同意后 ...
    ToolMessage(content="已修改 main.py", tool_call_id:"c2", name:"edit_file"),
    AIMessage(content="改好了，我加了一行注释。"),
]
```

**看清楚了吗？这是完整的工作记录**，每一步说了什么、调了什么、结果是什么，**逐字逐句保留**。没有摘要，没有提炼。

> 🔑 **核心结论①**：messages 里存的是**逐字原文的结构化消息流**，包括人话、工具调用、工具结果，全部保留。

## 3.4 「记忆」是怎么工作的：每轮把 messages 全塞给 LLM

既然 messages 是原文，那 LLM 怎么「记得」上文？

**答：每次调用 LLM，把当前 State 的 messages 全部塞进输入。**

在 `app/agent/nodes/agent_node.py`：

```python
async def agent_node(state, config, writer):
    messages = await compress_if_needed(state["messages"], thread_key=...)  # 太长才压缩，见 3.7
    if system_prompt:
        messages = [SystemMessage(content=system_prompt), *messages]
    request = build_chat_request(messages, tools)
    llm = get_llm_client()
    async for chunk in llm.stream_chat(request):
        ...
```

LLM 每次看到的输入是：`[系统提示, 用户第1句, AI第1答, 工具1结果, 用户第2句, AI第2答, 工具2结果, ...]`——**到目前为止的全部历史**。

它根据这些历史决定下一步。然后它的新回复**又被追加到 messages 里**，下一轮又会被塞进去。这就是「记忆」的真相：**不是 LLM 记得，是你的程序每次把完整历史端给它看。**

> 🔑 **核心结论②**：「记忆」= 把历史消息每次都塞进 LLM 输入。所以 messages 越长，token 越多，越贵越慢。这也解释了为什么要有「上下文压缩」（3.7）。

## 3.5 ★ 系统提示词（SystemMessage）：存不存？这是个关键设计

这是一个**特别容易踩坑**的点，本项目在这个坑里爬出来过。

### 错误做法（曾经的实现）

把系统提示词当作一条 SystemMessage **塞进 State 的 messages** 里。因为 messages 的 reducer 是「追加」语义（`add_messages`），结果：

- 第 1 轮：messages = `[系统提示, 用户1, AI1]`
- 第 2 轮：messages = `[系统提示, 用户1, AI1, 系统提示, 用户2, AI2]`  ← **又追加了一条系统提示**
- 第 N 轮：messages 里有 **N 份完整的系统提示**（每份还带着记忆、画像、RAG 检索结果）

**token 消耗呈平方增长。** 第 10 轮时 prompt 里有 10 份系统提示，第 100 轮……项目里专门有测试（`tests/test_regressions.py` 的 `test_system_message_does_not_accumulate_in_state`）钉住这个问题不再复发。

### 正确做法（现在）

**系统提示词不存进 State**。它通过 `config` 传给 agent 节点，每轮临时拼、临时用、用完即弃：

```python
# graph.py 的 run_agent / stream_agent
system_prompt = await _build_system_prompt_with_context(message, user_id, kb_ids, tenant_id)
config = {
    "configurable": {
        "thread_id": scoped_tid,
        "tools": get_all_tools(),
        "system_prompt": system_prompt,   # ← 走 config，不走 state
    },
    ...
}
```

agent_node 里：

```python
system_prompt = configurable.get("system_prompt")
if system_prompt:
    messages = [SystemMessage(content=system_prompt), *messages]  # 只拼进「发给 LLM 的这一份」
```

**SystemMessage 只出现在「发给 LLM 的临时一份」里，从不写回 State。** 所以不管多少轮，历史里都只有对话本身，系统提示永远只有一份。

> 🔑 **核心结论③**：系统提示词**不进持久化的 messages**。它每轮临时拼（含记忆/画像/RAG），通过 config 传给节点，用完即弃。这是避免「系统提示平方堆积」的关键设计。

### 那系统提示词本身存在哪？

它**不在 checkpointer 里持久化**。每轮调用时由 `_build_system_prompt_with_context()` 实时拼装：

```
基础人设（"你是 Self-Agent……"）
  + Hermes 反思后的优化版本（从 prompt_store 文件读）
  + Skill 提示词片段
  + 【知识库参考】RAG 检索结果（只在指定 kb_ids 时）
  + 【关于该用户的长期记忆】（只在有 user_id 时）
  + 【用户画像】兴趣/偏好
```

这些都是「这一轮的上下文」，每轮重新检索、重新拼。它们影响这一轮的回答，但不进历史。

## 3.6 工具结果太长怎么办：截断

工具可能返回 MB 级内容（爬网页、读大文件、MCP 返回大 JSON）。不截断的话，单条结果就能把上下文顶爆，后续所有轮次连带失败。

在 `app/agent/nodes/tools_node.py` 的 `_truncate()`：

```python
def _truncate(text: str, limit: int) -> str:
    if limit <= 0 or len(text) <= limit:
        return text
    omitted = len(text) - limit
    return f"{text[:limit]}\n\n...[输出过长，已截断 {omitted} 字符]"
```

`limit` 来自配置 `TOOL_RESULT_MAX_CHARS`。截断后的文本才进 ToolMessage。

**注意：截断发生在「写进 messages 之前」**。所以存进 checkpointer 的就是截断后的版本。这是少数「messages 里的内容不是完整原文」的地方——但这是有意的，防止历史被一条超大结果污染。

## 3.7 整段历史太长怎么办：上下文压缩（这里是「摘要」出现的地方）

到这里你可能会问：那 messages 一直涨，涨到 LLM 的 token 上限怎么办？

答案是 **`app/agent/context_manager.py` 的 `compress_if_needed()`**。这是全书里**唯一真正出现「摘要」**的地方。

策略（滑动窗口 + 摘要 + 摘要缓存）：

```python
DEFAULT_MAX_MESSAGES = 20   # 超过 20 条触发压缩
DEFAULT_KEEP_RECENT = 10    # 保留最近 10 条完整
_COMPRESS_EVERY = 6         # 迟滞窗口：攒够 6 条新早期消息才更新一次摘要

async def compress_if_needed(messages, *, thread_key=None, max_messages=20, keep_recent=10):
    if len(messages) <= max_messages:
        return messages  # 没超，不动
    # 把早期消息拿出来，用 LLM 摘要成一段
    to_summarize = dialog[:cut]      # 早期 N 条
    recent = dialog[cut:]            # 最近 10 条保留完整
    summary = await _generate_summary(to_summarize)  # 调一次 LLM
    return system_msgs + [SystemMessage("【早期对话摘要】\n" + summary)] + recent
```

**摘要缓存**（2026-08 性能改造加的）：上面是首次压缩的路径。如果每次都全量重摘，
长会话**每一轮**、ReAct 循环**每次回到 agent 节点**都要多调一次摘要 LLM——延迟和
token 双输。所以按 thread（`thread_key` 传 scoped thread_id）缓存
`{pos, id, summary}`（已摘要到哪、边界消息 id、摘要文本）：

- 新积累的早期消息 **< 6 条** → 直接复用旧摘要（近期暂时多保留几条，不调 LLM）；
- **≥ 6 条** → 做一次**增量摘要**：旧摘要 + 新消息一起喂给 LLM，输出合并版
  （比全量重摘省 token 也更快）；
- 边界消息 id 对不上（会话被重置/回放）→ 缓存作废，走全量重摘。

效果：摘要 LLM 调用从「每轮 1+ 次」降到「每 6 条新消息 1 次」。

**关键点**：

1. **压缩发生在「发给 LLM 之前」，不修改 State 本身**。`agent_node` 调用 `compress_if_needed(state["messages"], thread_key=...)`，拿到的压缩版只用于这一轮的 LLM 调用，State 里存的还是原文。
2. **只有触发阈值才压缩**（默认 20 条）。短对话根本不压缩，全是原文。
3. **压缩的是「早期对话」，最近 10 条始终完整保留**。这样 LLM 既有「全局发生了什么」的摘要，又有「最近细节」的原文。
4. 一个**安全细节**：被摘要掉的边界不能落在 ToolMessage 上——否则它对应的 AIMessage(tool_calls) 被摘要掉，会导致 ReAct 校验失败。代码里专门处理了这点（缓存复用路径同样保证）。

> 🔑 **核心结论④**：**checkpointer 存的是原文**。摘要只发生在「上下文超长时，临时压缩给 LLM 看」，不影响持久化的内容。所以你回来续聊时，看到的是完整原文。

## 3.8 ★ Checkpointer 到底存哪、存成什么格式

现在回答「存哪、什么形式」。

### 存储位置

由配置 `STORAGE_BACKEND` 决定（`app/memory/checkpointer.py`）：

| 后端 | 文件/位置 | 形态 | 何时用 |
|---|---|---|---|
| `sqlite` | `~/.local/share/selfagent/projects/<工作区路径哈希>/state.db` | 单文件 | **本地 CLI 模式**（CLI 启动时显式设置；全局默认是 `auto`） |
| `postgres` | PostgreSQL 表 | 持久化表 | 服务端模式 |
| `memory` | 进程内存 | 字典 | 兜底，重启即丢 |

### 「按项目分库」的设计

本地模式用工作区路径的 **SHA256 哈希前 16 位**做目录名（`app/memory/local_store.py:43`）：

```python
def sqlite_path_for(workspace: Path) -> Path:
    digest = hashlib.sha256(str(workspace.resolve()).encode()).hexdigest()[:16]
    project_dir = data_home() / "projects" / digest
    project_dir.mkdir(parents=True, exist_ok=True)
    # 留一份可读记录，否则一堆哈希目录没法排查
    marker = project_dir / "workspace.txt"
    if not marker.exists():
        marker.write_text(str(workspace.resolve()) + "\n")
    return project_dir / "state.db"
```

为什么要哈希？工作区路径可能很长、含空格或非 ASCII，直接当目录名跨平台会出问题。同时写一个 `workspace.txt` 记录原始路径，否则一堆哈希目录没法排查「哪个库对应哪个项目」。

**同项目历史能续上，换目录就是新开始。** 这是「工作区是编码 Agent 的上下文单位」这条原则的体现。

### 存进 SQLite/Postgres 的具体格式

LangGraph 的 checkpointer 不存「消息文本」，它存的是**序列化后的整个 channel 状态**：

- 把 `messages` 列表（一串消息对象）序列化成字节流（默认用类 MsgPack 或 JSON）
- 加上版本号、checkpoint_id、节点消费进度等元数据
- 按 `thread_id` 为键存进表

打开 SQLite 文件，你会看到几张 LangGraph 的内部表（`checkpoints`、`writes` 等），里面是序列化的 blob，不是人类可读的文本。

> 这意味着：**你不能直接用 `sqlite3` 命令读出对话历史**。要读历史得用 LangGraph 的 API（`graph.get_state_history(config)`）。这是 checkpointer 的代价——换来的是事务可靠性、中断恢复、跨进程共享。

### 什么时候存？

**每走一步存一次**。具体说：

- agent 节点跑完 → 存一次（messages 多了一条 AIMessage）
- tools 节点跑完 → 存一次（messages 多了若干 ToolMessage）
- interrupt 挂起时 → 存一次（状态完整保存，等恢复）

所以「中断恢复」能工作：因为挂起那一刻的完整 State 已经在 checkpointer 里了，恢复时按 `thread_id` 读回来，从 interrupt 那行继续。

## 3.9 三个「记忆」概念，别搞混

到这里经常有人糊涂：「短期记忆」「长期记忆」「对话日志」到底啥区别？

| 名称 | 存什么 | 存哪 | 用途 | 存的形式 |
|---|---|---|---|---|
| **短期记忆**（checkpointer） | 对话历史 messages + plan | SQLite/Postgres | 同一会话续接上下文、中断恢复 | **原文**（结构化消息） |
| **长期记忆**（store） | 跨会话的用户事实（「他是 Python 工程师」「偏好简洁回答」） | Store（Postgres/内存） | 跨会话记住用户，注入系统提示 | **抽取的事实文本**（带向量） |
| **对话日志**（MongoDB） | 每轮的完整事件（输入/输出/工具/耗时/token） | MongoDB | 审计、统计、Hermes 反思 | **事件流**（即发即忘） |

记住：

- **短期 = 这一轮对话的原文历史**（这是本章讲的 State/messages）
- **长期 = 跨对话的事实**（第 7 章详讲，是 Hermes 从对话里抽取的，不是对话本身）
- **日志 = 给人看的审计记录**（不是给 LLM 看的）

## 3.11 外部世界怎么做

| 项目 | 状态/记忆怎么存 |
|---|---|
| **LangGraph**（本项目用的） | StateGraph + channel/reducer + checkpointer。状态严谨、可中断恢复，工业级 |
| **OpenAI Agents SDK** | Sessions 管理会话状态，较轻量 |
| **AutoGen** | 对话历史 + 事件队列，长对话会膨胀 |
| **MemGPT / Letta** | 仿操作系统的**虚拟内存分页**——主上下文 + 归档层，agent 自己 page in/out。学习曲线陡但上下文管理极强 |
| **Mem0** | 专门的记忆层，抽取式记忆 + 向量/图库。易上手、基准性能好 |
| **Aider** | 代码场景：tree-sitter 解析仓库 + 图排序，选最相关的代码塞进上下文（repo-map） |

**核心区分**：MemGPT/Letta 做的是**上下文管理**（让 agent 意识到上下文有限并主动管理），Mem0 做的是**记忆存储/检索层**。本项目的「短期/长期」可以对照：短期≈LangGraph channel，长期≈Mem0 式分层。详见拆解④。

## 3.12 面试一句话

> **Q：Agent 怎么实现多轮记忆？**
> A：不是 LLM 自己记，是程序把历史消息存在 checkpointer 里，每次调用 LLM 时把完整历史塞进输入。本项目用 LangGraph 的 checkpointer，每步存一次，按 thread_id 续接。

> **Q：为什么系统提示不存进 state？**
> A：因为 messages 是追加语义，存进去每轮都会多一份，token 平方增长。所以系统提示走 config 临时传，用完即弃。

> **Q：上下文超长怎么办？**
> A：临时压缩——把早期对话摘要成一段，最近几条保留完整，只给 LLM 看压缩版。持久化的仍是原文。
