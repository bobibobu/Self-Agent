# 第 12 章：完整链路拆解

> 跟着「读一下 main.py，然后加个注释」这句话，从你敲下回车到看到最终回答，**每一步代码级跟踪**。

## 12.1 全景图

```
你在终端敲下这句话
   │
   ▼
① CLI 接住 ──────────────────────────── clients/cli/selfagent_cli/localrepl.py:62 _drive()
   │
   ▼
② 组装系统提示词 ────────────────────── app/agent/graph.py:228 _build_system_prompt_with_context()
   │  （身份设定 + 长期记忆 + 用户画像 + 知识库检索结果 + Skill 提示）
   │  ★ 这段不存进 State，每轮临时拼
   ▼
③ 进入 LangGraph 状态图 ─────────────── app/agent/graph.py:366 stream_agent()
   │
   ├─→ agent 节点：问大模型 ─────────── app/agent/nodes/agent_node.py:41
   │      ★ 先 compress_if_needed（太长才压缩；摘要带 per-thread 缓存，不会每轮重摘）
   │      ★ 系统提示临时拼到最前面，不写回 State
   │      大模型答："我要调 read_file(main.py)"
   │      同时逐字把思考过程流出来给你看（writer token 事件）
   │      AIMessage 追加到 messages
   │
   ├─→ 条件路由：should_use_tools ────── app/agent/nodes/tools_node.py:202
   │      有 tool_calls → 去 tools 节点
   │
   ├─→ tools 节点 ──────────────────── app/agent/nodes/tools_node.py:176
   │      ★ 并发执行所有 tool_calls（asyncio.gather）
   │      每个 call 走 _run_one 流水线：
   │        1. 策略检查（readonly 模式拒绝写/执行）
   │        2. 审批检查 needs_approval()
   │           read_file 是 READ → 不问 → 直接执行
   │        3. get_tool("read_file") 从注册表查

   │        5. 截断到 TOOL_RESULT_MAX_CHARS
   │        6. ToolMessage 塞回 State
   │      checkpointer 存档（messages 多了 ToolMessage）
   │
   ├─→ 回到 agent 节点：大模型看到文件内容了
   │      答："我要调 edit_file 加注释"
   │      AIMessage(tool_calls=[edit_file]) 追加
   │
   ├─→ tools 节点：edit_file 是 WRITE 级
   │      needs_approval() = True → interrupt() ⏸
   │      ★ 图在这里挂起，State 完整存进 checkpointer
   │      吐出 {"type": "approval_required", "tool":"edit_file", ...}
   │      事件流自然结束（不发 done，因为还没完）
   │
   │   ...你在终端按了 y...
   │
   ├─→ resume_agent(thread_id, {"approved": True})
   │      LangGraph 从 checkpointer 读回 State
   │      从 interrupt() 那一行原地继续，返回决策
   │      edit_file 真的执行（在沙箱里，如果涉及命令）
   │      ToolMessage("已修改 main.py") 塞回
   │
   ├─→ 回到 agent 节点：大模型说"改好了"
   │      AIMessage("改好了，我加了一行注释。") 无 tool_calls
   │
   └─→ 条件路由：无 tool_calls → END
   │
   ▼

   │
   ▼
⑤ 后台 fire-and-forget（不阻塞你）：
```

## 12.2 逐步细说

### ① CLI 接住输入

`localrepl.py` 的 `_drive()`。它做三件事：

1. 调用 `stream_agent()` 拿到一个**事件流**
2. 把事件渲染到终端
3. 遇到审批请求就问你

事件流长这样（一个个字典，统一格式）：

```python
{"type": "token", "text": "我"}         # 大模型吐的字，逐个来
{"type": "token", "text": "先"}
{"type": "tool_calls", "calls": [...]}   # 它决定调工具了
{"type": "tool_start", "name": "read_file"}
{"type": "tool_result", "name": "read_file", "content": "..."}
{"type": "approval_required", "tool": "edit_file", ...}  # 需要确认
{"type": "done", "reply": "完整回答"}
```

**关键**：拿到 `approval_required` **不能 break**。LangGraph 要等 astream 自然结束才会把中断状态写进 checkpointer；提前中止会让 resume 找不到可恢复的中断——表现为「点了同意但什么都没发生」。`consume()` 内部函数专门处理这点：记下 approval 但继续把流走完。

### ② 组装系统提示词

`graph.py:228` 的 `_build_system_prompt_with_context()`。这一段是「回答开始前」的全部准备工作，单独成 span——它由若干次网络往返（向量化 + 检索 + 图查询）组成，出问题时首字延迟会被它拖高，但从外面完全看不出来是卡在这里。

```
基础人设（"你是 Self-Agent，工作原则是……"；当前时间已移出，走 config 拼到对话末尾保缓存前缀）
  ＋ Hermes 反思后的优化版本（从 prompt_store 动态读）
  ＋ Skill 提示词片段
  ＋ 【知识库参考】RAG 检索结果（只在指定 kb_ids 时）
  ＋ 【关于该用户的长期记忆】（语义检索 top-3，只在有 user_id 时）
  ＋ 【用户画像】兴趣/偏好
```

**★ 核心设计**：这段提示词**不存进 State 的 messages**。它通过 `config["configurable"]["system_prompt"]` 传给节点，每轮临时拼、临时用、用完即弃（第 3 章详细解释过为什么——否则平方堆积）。

### ③ 进入状态图：stream_agent

`graph.py:366` 的 `stream_agent()` 是对外入口：

```python
async def stream_agent(message, thread_id, user_id=None, kb_ids=None, tenant_id="default"):
    async for event in _stream_graph(None, thread_id=thread_id, ...):
        yield event
```

`_stream_graph` 是 stream_agent 和 resume_agent 共用的主体。两者唯一区别是喂给 graph.astream 的输入：首次是 `{"messages": [HumanMessage]}`，续跑是 `Command(resume=决策)`。

config 组装：

```python
config = {
    "configurable": {
        "thread_id": scoped_tid,       # 多租户加前缀
        "tools": get_all_tools(),      # 工具清单
        "system_prompt": system_prompt, # 侧通道，不进 state
    },
    "recursion_limit": get_settings().agent_recursion_limit,  # 防死循环
}
```

注册流式任务（支持取消）：`register_stream(thread_id)`，用原始 thread_id 作 cancel key。

然后 `graph.astream(graph_input, config, stream_mode=["custom","updates"], version="v2")`。

### ④ agent 节点

`agent_node.py:41`。核心是一次**流式调用**：

```python
async def agent_node(state, config, writer):
    configurable = config.get("configurable", {})
    system_prompt = configurable.get("system_prompt")

    # 上下文窗口管理：太长才压缩（第 3 章）；thread_key 启用摘要缓存
    messages = await compress_if_needed(state["messages"], thread_key=configurable.get("thread_id"))

    # 系统提示只拼进「发给 LLM 的这一份」，不写回 state
    if system_prompt:
        messages = [SystemMessage(content=system_prompt), *messages]

    request = build_chat_request(messages, tools)  # bridge.py 翻译
    llm = get_llm_client()

    with llm_span(...) as sp:
        async for chunk in llm.stream_chat(request):
            if chunk.content:
                content_parts.append(chunk.content)
                writer({"type": "token", "text": chunk.content})  # 逐字吐
            if chunk.tool_calls:
                tool_calls_list = chunk.tool_calls  # 流末尾聚合完整
            if chunk.usage:
                usage = chunk.usage

    ai_msg = AIMessage(content=full_text, tool_calls=..., additional_kwargs={...})
    return {"messages": [ai_msg]}  # add_messages reducer 追加
```

一次调用同时拿到「要说的话」和「要调的工具」（第 5 章解释过为什么——避免两次采样）。

### ⑤ 条件路由

`tools_node.py:202` 的 `should_use_tools`：

```python
def should_use_tools(state) -> str:
    last_msg = state["messages"][-1]
    tool_calls = getattr(last_msg, "tool_calls", None)
    if tool_calls:
        return "tools"
    return "end"
```

看最后一条消息有没有 tool_calls。有就去 tools，没有就 END。**ReAct 循环的路由器，一行 if-else。**

### ⑥ tools 节点

`tools_node.py:176`：

```python
async def tools_node(state, config, writer):
    last_msg = state["messages"][-1]
    tool_calls = getattr(last_msg, "tool_calls", None) or []
    # 并发执行
    results = await asyncio.gather(*(_run_one(c, writer, limit) for c in tool_calls))
    messages = [msg for msg, _ in results]
    updates = {}
    for _, upd in results:
        updates.update(upd)
    return {"messages": messages, **updates}
```

`_run_one` 流水线（第 6 章）：策略检查 → 审批检查 → 找工具 → 执行 → 截断 → 返回。

**read_file**：READ 级，不审批。路径过 `Workspace.resolve()` 禁闭。读到内容，截断，ToolMessage 塞回。

**edit_file**：WRITE 级，`needs_approval()` = True：

```python
if needs_approval(name):
    decision = interrupt({  # ← 图挂起
        "type": "tool_approval",
        "tool": name, "risk": ..., "args": args, "call_id": call_id,
    })
    approved, reason = _parse_decision(decision)
    if not approved:
        return ToolMessage(content="用户拒绝了此操作...", ...)
```

`interrupt()` 让整张图停下来。这不是普通暂停——LangGraph 把当前状态完整存进 checkpointer，然后事件流自然结束。

### ⑦ 审批中断与恢复（最绕的一步）

```
第一次调用 stream_agent()
   ↓ ...跑到 edit_file 审批...
   ↓ interrupt() → 图挂起，状态落盘
   ↓ 吐出 {"type": "approval_required", ...} 事件
   ↓ 事件流结束（不发 done）

   ——— 你在终端按 y ———

调用 resume_agent(thread_id, {"approved": True})
   ↓ graph.astream(Command(resume=decision), config)
   ↓ LangGraph 从 checkpointer 读回状态
   ↓ 从 interrupt() 那一行原地继续，返回 {"approved": True}
   ↓ edit_file 真的执行
   ↓ 继续走完剩下的循环
```

`graph.py:346` 的 `resume_agent`：

```python
async def resume_agent(thread_id, decision, *, user_id=None, tenant_id="default"):
    from langgraph.types import Command
    async for event in _stream_graph(
        Command(resume=decision), thread_id=thread_id, ...,
        resuming=True,
    ):
        yield event
```

续跑**不重建系统提示**：图是从 interrupt() 原地恢复的，上下文（含系统提示）还在这一轮的执行状态里。

### ⑧ 任务计划（多步任务才有）

如果任务三步以上，大模型会先调 `update_plan` 列计划：

```
╭─ 任务计划 1/3 ─╮
│ ✔ 读懂 main.py │
│ ▶ 添加注释     │
│ ○ 验证结果     │
╰────────────────╯
```

计划存在 State 里随 checkpointer 持久化（第 9 章）。每轮 update_plan 返回渲染文本给模型看，同时推 `plan_updated` 事件让客户端渲染常驻面板。

### ⑨ 结束与收尾

agent 节点返回无 tool_calls 的 AIMessage → `should_use_tools` 返回 "end" → 图结束。

`_stream_graph` 在 finally 后：

```python
reply = "".join(full_reply_parts)
yield {"type": "done", "thread_id": thread_id, "reply": reply, "error": error}

# 后台 fire-and-forget（不阻塞用户）
_spawn(_log_conversation(...))           # MongoDB 日志
if message:
    _maybe_learn(...)                    # Hermes 学习
_touch_session(...)                      # 更新会话
```

## 12.3 用 trace 看一次完整的执行

开启 `OTEL_ENABLED=true`，在 Jaeger（http://localhost:16686）能看到这棵 span 树：

```
agent.turn                        5078.2ms
├─ graph.compile                  5061.4ms   ← 首次请求才有（启动已预热）
├─ context.build                     4.4ms
│  ├─ rag.retrieve                   0.3ms   chunk_count=3
│  ├─ memory.search                  0.1ms   memory_hits=2
│  └─ profile.get                    0.0ms
├─ chat glm-4.5-flash              820.0ms   input_tokens=312 output_tokens=24 tool_call_count=1
├─ execute_tool read_file            0.7ms
└─ chat glm-4.5-flash              610.0ms   input_tokens=381 output_tokens=17
```

这棵树直接回答：
- **首字延迟卡在哪**：context.build 还是 chat
- **调了几次 LLM**：两个 chat span = 两次（第一次决定调工具，第二次总结）
- **token 花在哪步**：每个 chat span 的 input/output_tokens
- **工具耗时**：execute_tool 的耗时

**这是理解「时间花在哪」最直观的方式。**
