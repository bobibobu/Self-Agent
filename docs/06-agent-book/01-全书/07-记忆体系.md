# 第 7 章：记忆体系

> 目标：读完这章，你能精确区分「短期/长期/画像/日志」四层记忆，知道它们各自存什么、存哪、怎么用。

---

## 7.1 为什么需要这么多层记忆

没有记忆的 LLM 是「金鱼」——每次对话从零开始。真实场景需要：

| 场景 | 需要的记忆 |
|---|---|
| 「我刚才说的那件事」 | **短期记忆**（本次对话内） |
| 「用户喜欢简洁回答」 | **长期记忆**（跨对话） |
| 「上周聊了什么」 | **对话日志**（历史回溯） |
| 「用户是 Python 开发者」 | **用户画像**（结构化属性） |

四种需求**形态完全不同**，所以用四个东西分别处理。这叫**多语言持久化（polyglot persistence）**——每个存储用在其强项上。

---

## 7.2 四层记忆对照表

| 层 | 存什么 | 存哪 | 用途 | 形态 |
|---|---|---|---|---|
| **短期** | 对话历史 messages + plan | SQLite/Postgres | 同会话续接、中断恢复 | 原文消息流（第 3 章详讲） |
| **长期** | 跨会话的用户事实 | Store（Postgres/内存） | 跨会话记住用户，注入系统提示 | 抽取的事实文本 + 向量 |
| **画像** | 兴趣/偏好/属性 | Neo4j | 结构化属性分析 | 实体-关系图 |
| **日志** | 每轮完整事件 | MongoDB | 审计、统计、反思 | 事件流（即发即忘） |

---

## 7.3 短期记忆（Checkpointer）

第 3 章已经彻底讲过。这里只回顾要点：

- **本质**：把历史消息存进 checkpointer，下次调用时按 thread_id 取回，塞进 LLM 输入
- **存的是原文**（结构化消息对象，不是摘要）
- **本地用 SQLite**（按工作区分库），服务端用 Postgres，兜底内存
- **每步存一次**，所以能中断恢复

代码：`app/memory/checkpointer.py`。

---

## 7.4 ★ 长期记忆（Store）：跨会话的事实

这是和短期最容易混淆的一层。

### 它存什么

**不是对话本身**，是从对话里**抽取出来的事实**：

```
"用户在学 LangGraph"
"用户偏好简洁回答"
"用户在做微服务项目"
```

这些是跨会话稳定的、关于用户的**事实**。下次新对话（新 thread_id）时，短期记忆是空的，但长期记忆还在。

### 怎么来的

两个途径：
1. **显式 API**：`POST /memory {"user_id":"u1", "content":"用户偏好简洁回答"}`
2. **Hermes 自动抽取**（`app/evolution/memory_learner.py`）：每轮对话后异步用轻量 LLM 抽「值得记住的事实」，写入画像/记忆（fire-and-forget，第 11 章详讲）

### 怎么检索：语义检索（embedding）

这是长期记忆和短期记忆最大的区别。短期记忆是「按 thread_id 取全部」，长期记忆是「**按语义相关性**检索 top-N」。

为什么需要语义检索？因为长期记忆可能很多，不可能全塞进系统提示。要挑**和当前问题最相关的**几条。

怎么挑？用 **embedding**（向量化）：

1. 存记忆时，把文本转成一个向量（一串数字）
2. 查询时，把用户的问题也转成向量
3. 算两个向量的余弦相似度，取最相似的几条

**为什么需要 embedding 而不是关键词匹配**：关键词匹配不懂语义。「编程偏好」和「写代码喜欢」字面不同但语义相近，关键词匹配找不到，embedding 能找到。

### 哈希伪向量（开发期降级）

没配 embedding key 时，本项目用**确定性字符哈希**当伪向量：

```python
# 简化版：把文本哈希成一个固定维度的向量
def fake_embedding(text: str) -> list[float]:
    # 基于字符的哈希，确定性但不理解语义
    ...
```

**为什么只在开发用**：它是字符哈希，没有真实语义理解能力（「猫」和「狗」的向量不会比「猫」和「汽车」更近）。开发期能让接口跑通即可；生产必须用真实 embedding 模型（捕捉语义）。启动日志里有 WARNING。

### 怎么注入对话

在 `_build_system_prompt_inner()`（`graph.py:239`）：

```python
if user_id:
    memories = await mem_service.search_memory(user_id, user_message, limit=3)
    if memories:
        mem_text = "\n".join(f"- {m['content']}" for m in memories if m.get("content"))
        base += f"\n\n【关于该用户的长期记忆】\n{mem_text}"
```

按 namespace 隔离：`("user", user_id)`。多租户下加前缀 `("tenant", tenant_id, "user", user_id)`。

代码：`app/memory/store.py`、`app/memory/embeddings.py`。

## 7.5 用户画像（Neo4j）：结构化的属性

长期记忆是自由文本，画像是**结构化的实体-关系**。

### 数据模型

```
(User)-[:INTERESTED_IN]->(Topic)
(User)-[:PREFERS]->(Preference)
```

例子：
- `(用户 u1)-[:INTERESTED_IN]->(机器学习)`
- `(用户 u1)-[:PREFERS]->(回答风格=详细)`

### 为什么用图数据库不用关系型

用户画像是「实体-关系」密集型数据，核心查询是**多跳关系遍历**（如「朋友也感兴趣的话题」）。

关系型 DB 的 JOIN 在 3 跳以上性能急剧下降（O(n^深度)），Neo4j 图遍历**每跳 O(1)**（邻接表存储，关系是一等公民）。

这是「多语言持久化」的体现：每个数据库用在其强项——对话状态用 Postgres（事务），日志用 Mongo（无 schema），限流用 Redis（内存计数），画像用 Neo4j（图）。

### API

```
POST /profile/interest   {"user_id":"u1", "interest":"人工智能"}
POST /profile/preference {"user_id":"u1", "key":"回答风格", "value":"详细"}
GET  /profile/u1         → {interests:["人工智能"], preferences:{"回答风格":["详细"]}}
```

### 怎么注入

和长期记忆一起，在系统提示里：

```
【关于该用户的长期记忆】        ← 自由文本（语义检索）
- 用户在学 LangGraph
【用户画像】                    ← 结构化属性
兴趣：人工智能、系统设计
偏好：回答风格=详细
```

代码：`app/profile/service.py`。优雅降级：Neo4j 不可用时用内存 dict 兜底，`source` 字段标识来源。

## 7.6 对话日志（MongoDB）：给人看的记录

### 它存什么

每轮对话的**完整事件**：

```json
{
  "thread_id": "...",
  "user_id": "u1",
  "user_message": "北京天气？",
  "agent_reply": "北京今天晴 26 度...",
  "duration_ms": 1234,
  "error": null,
  "tenant_id": "default",
  "provider": "glm",
  "usage": {"prompt_tokens": 312, "completion_tokens": 24}
}
```

### 为什么用 MongoDB

- 日志**形态多变**（有的轮次有工具调用、有的没有）
- **写多读少**（每轮都写，偶尔查）
- **无 schema** 正合适

关系型 DB 也能做，但 Mongo 的文档模型对「形态多变的日志」最自然。

### 「即发即忘」设计

在 `graph.py` 里：

```python
# 记录对话日志：真正的 fire-and-forget（不阻塞响应）
_spawn(_log_conversation(thread_id=..., user_message=..., agent_reply=..., ...))
```

`_spawn` 是 fire-and-forget 后台任务。**日志记录失败不影响对话主流程**——这是优雅降级原则：核心链路尽量独立于非关键依赖。

### 谁消费日志

- **审计**：`GET /history/t1` 看会话历史
- **统计**：`GET /stats/usage`（请求数、token、成本估算）
- **Hermes 反思**：取近期对话样本，LLM 自评提示词表现，生成优化版（第 11 章）

代码：`app/logging_service/__init__.py`。

## 7.7 四层记忆怎么协作

用「我在学 LangGraph，是 Python 开发者，喜欢详细回答」走一遍：

```
你说这句话
  ↓
① 短期记忆：这句话进 messages，checkpointer 存档
  ↓
② Hermes 异步学习（后台，不阻塞你）：
     LLM 抽取 → {"interests":["LangGraph"], "preferences":{"风格":"详细"}, "facts":["Python开发者"]}
       ↓
       兴趣 → Neo4j 用户画像（画像层）
       偏好 → Neo4j 用户画像（画像层）
       事实 → Store 长期记忆（长期层，向量化）
  ↓
③ 整轮事件 → MongoDB 日志（日志层）
  ↓
④ 下次新对话时：
     系统提示 = 基础人设 + 【长期记忆】(语义检索 top-3) + 【画像】(结构化属性)
     LLM 看到这些，个性化回答
```

四层各司其职：短期管「这一轮」，长期管「跨轮的事实」，画像管「结构化属性」，日志管「审计统计」。

## 7.8 外部世界怎么做

| 项目 | 记忆怎么做 |
|---|---|
| **LangGraph checkpointer + Store**（本项目） | 短期 channel + 长期 Store，工业级 |
| **OpenAI Sessions** | 会话状态，较轻量 |
| **AutoGen** | 对话历史 + 事件队列，长对话会膨胀 |
| **MemGPT / Letta** | **仿 OS 的虚拟内存分页**——主上下文 + 归档层，agent 自己 page in/out，自编辑。学习曲线陡但上下文管理极强 |
| **Mem0** | 专门的记忆层，抽取式记忆 + 向量/图库。易上手、基准性能好 |
| **Aider** | 代码场景：tree-sitter repo-map + 图排序选最相关代码 |

### 关键区分

- **MemGPT/Letta** 做的是**上下文管理**——让 agent 意识到上下文有限并主动管理（像 OS 管内存）
- **Mem0** 做的是**记忆存储/检索层**——抽取、存储、检索，但不主动管理上下文
- **本项目** 的「短期/长期」对照：短期≈LangGraph channel，长期≈Mem0 式分层。详见拆解④。

## 7.9 面试一句话

> **Q：短期和长期记忆边界在哪？**
> A：短期是「本次对话」的上下文（checkpointer，按 thread），长期是「跨对话」的用户事实（store，按 namespace）。短期对话结束即可丢，长期跨会话持久化。

> **Q：为什么语义检索需要 embedding？**
> A：关键词匹配不懂语义（"编程偏好" ≠ "写代码喜欢"但语义相近）。embedding 把文本映射到向量空间，相似语义向量距离近，支持「按意思」检索。

> **Q：为什么画像用 Neo4j 不用关系型？**
> A：画像是实体-关系密集型，核心查询是多跳关系遍历。关系型 3 跳以上 JOIN 性能急剧下降，Neo4j 图遍历每跳 O(1)。多语言持久化，各 DB 用在其强项。
