# 第 14 章：架构范式总览

> 把所有 Agent 项目按「架构范式」分类，让你看清它们各自落在哪一档、为什么这么选。

---

## 14.1 单 Agent 的五种范式

| 范式 | 核心思想 | 适用场景 | 典型实现 | Self-Agent 在哪 |
|---|---|---|---|---|
| **ReAct** | Thought→Act→Observation 交错循环 | 动态、需用工具、信息会变 | LangGraph 默认 agent、OpenAI SDK | **✓ 本项目** |
| **Plan-and-Execute** | 先用 planner 出完整计划，再逐步执行 | 多步任务、规划是瓶颈 | BabyAGI、Aider Architect/Editor | 部分（任务计划） |
| **Reflexion** | 失败后自我反思、用「语言强化学习」改进 | 需纠错和迭代改进 | 学术原型；常与 ReAct 叠加 | 部分（Hermes） |
| **Multi-Agent** | 多 agent 分工协作/对话/转交 | 复杂任务、需多视角 | AutoGen GroupChat、CrewAI、MetaGPT | 部分（A2A） |
| **Router/Orchestrator** | 调度器决定路由到哪个子 agent/工具 | 分类分发、降低单 prompt 复杂度 | OpenAI handoffs、CrewAI hierarchical | — |

---

## 14.2 ReAct（本项目的核心）

最经典的 Agent 范式。第 1 章详细讲过。

**特点**：思考与行动交错，每一步根据上一步观察决定下一步。

**优点**：动态、灵活，信息会变的任务（天气、实时数据）必选。

**缺点**：单层 ReAct 扛不住长任务——走到第七八步会忘记最初目标。这就是为什么本项目加了**任务计划**（外部记事板）。

**本项目位置**：核心就是 ReAct（`agent` ↔ `tools` 条件路由）。

---

## 14.3 Plan-and-Execute

**核心思想**：把「规划」和「执行」分开。先用一个（可能更便宜的）planner 出完整计划，再逐步执行。

**代表**：
- **BabyAGI**：create_task → prioritize_task → execute_task 循环
- **Aider Architect/Editor**：Architect 模型只推理描述怎么改，Editor 模型负责落地——这个分工在 SWE-bench 风格基准上刷新了 SOTA

**和 ReAct 的关系**：Plan-and-Execute 常和 ReAct 叠加——计划阶段用 Plan，每个子任务内部用 ReAct 执行。

**本项目**：有任务计划（`update_plan`），但本质还是单层 ReAct。**已知限制**：无子 Agent / 并行分解（README 明确列出）。如果要升级，Aider 的 Architect/Editor 双模型是参考方向。

---

## 14.4 Reflexion（自我反思）

**核心思想**：失败后让 agent 自我反思，把「这次为什么失败、下次怎么改」写进记忆，下次做得更好。本质是「语言强化学习」。

**代表**：学术原型；常与 ReAct 叠加使用。

**和本项目的对应**：Hermes 的**反思 + 提示词自优化**（能力 B）就是 Reflexion 思想的应用——取近期对话，LLM 自评提示词表现，生成优化版。

**Reflexion 的风险**：反思可能越改越差。本项目的控制：评分阈值（< 6.0 不采纳）+ 版本管理（可回滚）+ 不无限自改（手动触发）。详见第 11 章。

---

## 14.5 Multi-Agent（多 Agent 协作）

**核心思想**：多个 agent 分工，每个负责一部分，协作完成复杂任务。

四种「多人协作」隐喻（高价值对比）：

| 隐喻 | 代表 | 特点 |
|---|---|---|
| **群聊** | AutoGen GroupChat | 多 agent 围绕对话轮流发言，像开会讨论 |
| **接力** | OpenAI handoffs | Agent 间显式转交控制权，上下文随之迁移 |
| **剧本角色** | CrewAI / MetaGPT | 每个 agent 有 role/goal/backstory，像剧本角色 |
| **任务委派** | **A2A（本项目）** | Agent 间通过标准协议派工单，对等体 |

**本项目位置**：A2A（任务委派）。`delegate_to_agent` 工具让 LLM 自主决定何时委托外部 Agent。

**为什么选 A2A 而不是群聊/接力/角色**：
- **标准化**：A2A 是开放标准（Google/Linux Foundation），不绑框架
- **解耦**：不透明对等体，不共享内部，任意实现都能互通
- **去中心化发现**：`/.well-known/agent-card.json`，DNS 式

代价：比群聊/角色更「重」，需要双方都实现协议。详见拆解②③。

---

## 14.6 Router / Orchestrator

**核心思想**：一个调度器（router/orchestrator）决定把请求路由到哪个子 agent 或工具。降低单个 prompt 的复杂度。

**代表**：OpenAI handoffs（本质上 handoff 就是一种路由）、CrewAI hierarchical（manager agent 调度子 agent）。

**适用**：分类分发场景（客服路由到不同领域 agent）。

**本项目**：当前没有显式的 router 节点，但 `delegate_to_agent` 工具 + LLM 自主决策本质上是「LLM 当 router」。

---

## 14.7 生产建议（综合多份资料）

- **ReAct + Reflexion 是单 Agent 生产级标配**
- 规划成为瓶颈时上 **Plan-and-Execute**
- 需要校验时加 **verifier/critic**
- 多人协作优先考虑 **标准化协议（A2A）** 而非自研

本项目：ReAct（核心）+ Reflexion（Hermes）+ 任务计划（轻量 Plan）+ A2A（Multi-Agent）。覆盖了主流范式的核心组合。

---

## 14.8 编排哲学四象限（重申）

| 派别 | 代表 | 哲学 |
|---|---|---|
| **图驱动** | LangGraph（本项目） | 用状态图描述流程，状态严谨可恢复 |
| **事件驱动** | LlamaIndex Workflows / AutoGen v0.4 | 用 event+handler 组织，消息驱动 |
| **流程驱动** | CrewAI / MetaGPT | 把人类 SOP 固化成剧本 |
| **协议驱动** | Self-Agent（MCP+A2A） | 靠标准协议接入生态 |

本项目是「图驱动内核 + 协议驱动扩展」的混合——内核用 LangGraph 跑 ReAct，扩展用 MCP/A2A 接生态。这是个很务实的选择：内核要稳所以用最严谨的图，扩展要活所以用最开放的协议。

## 14.9 状态/记忆范式总览

| 方案 | 机制 | 特点 |
|---|---|---|
| **LangGraph Checkpointer**（本项目） | channel+reducer，序列化持久化，支持中断恢复 | 工业级短期/会话状态 + HITL |
| **AutoGen 对话历史** | 消息列表 + 事件队列 | 简单，但长对话膨胀 |
| **MemGPT / Letta** | OS 启发的虚拟内存分页——主上下文 + 归档层，agent 自己 page in/out | 上下文管理（非纯存储），学习曲线陡 |
| **Mem0** | 专门的记忆层/API，抽取式记忆 + 图/向量库 | 基准性能好，易上手 |
| **Aider repo-map** | tree-sitter + 图排序的结构化代码记忆 | 编码场景特化 |

**核心区分**：
- MemGPT/Letta 做**上下文管理**（让 agent 意识到上下文有限并主动管理）
- Mem0 做**记忆存储/检索层**
- 本项目的「短期/长期」对照：短期≈LangGraph channel/会话状态，长期≈Mem0 式分层

## 14.10 怎么选型（给要做新项目的人）

| 你的需求 | 推荐范式/工具 |
|---|---|
| 快速搭一个能调工具的 Agent | ReAct（LangGraph 或 OpenAI SDK） |
| 长任务、规划是瓶颈 | Plan-and-Execute（Aider Architect/Editor 模式） |
| 要自我改进 | ReAct + Reflexion（本项目 Hermes 模式） |
| 多人协作、要标准化 | A2A 协议 |
| 多人协作、要直觉化 | CrewAI 角色化 |
| 上下文经常爆 | MemGPT/Letta 式虚拟内存 |
| 跨会话记住用户 | Mem0 / 本项目的 Store + 画像 |
| 编码场景 | Aider repo-map + 工作区禁闭 + 沙箱（本项目模式） |
| 接入大量外部工具 | MCP |
| 企业级可观测 | OpenTelemetry GenAI 约定 |

**本项目几乎是上面所有需求的一个综合实现**——这也是为什么它适合当学习蓝本：读懂它，就摸到了所有范式的门道。

---

## 14.11 一个诚实的认知

**没有银弹。** 每种范式、每个框架都是在解决特定问题时的取舍：

- ReAct 灵活但扛不住长任务
- Plan-and-Execute 稳但不够动态
- Multi-Agent 强大但复杂、易失控
- 协议驱动开放但要双方实现
- 图驱动严谨但学习曲线陡

选型的本质是**认清你的约束**（任务类型、团队、规模、安全要求），然后选最匹配的范式组合。本项目选「ReAct 内核 + 任务计划 + A2A + 三层安全 + 四层记忆」是因为它定位是「企业级、全功能、学习友好」——如果你的定位不同，组合也该不同。
