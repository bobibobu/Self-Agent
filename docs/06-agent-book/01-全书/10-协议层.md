# 第 10 章：协议层

> 目标：读完这章，你能讲清楚 MCP、A2A、Skill 三种扩展机制**各自解决什么、怎么配合**。

---

## 10.1 三种扩展，三个层次

Self-Agent 不只是「调内置工具」，它有三种「让 Agent 变强」的机制：

| 机制 | 解决什么 | 一句话 |
|---|---|---|
| **MCP** | 接外部工具/数据源 | AI 应用的 USB-C |
| **A2A** | Agent 间互相协作 | Agent 世界的 HTTP |
| **Skill** | 打包「工具+提示词」成能力单元 | Agent 的插件 |

三者互补不冲突。本项目**同时**是 MCP client + MCP server + A2A server + A2A client + Skill 容器。

---

## 10.2 MCP（Model Context Protocol）

Anthropic 2024 年提出的开放标准。解决「M 个 LLM × N 个工具 = M×N 集成爆炸」问题。

### 痛点

每个 Agent 框架的工具接口各不相同。写一个工具（比如「查 GitHub issue」）要在 LangChain、OpenAI SDK、AutoGen……里适配 N 次。换 LLM 又要重写。

### MCP 的解法：统一协议

像 USB-C 一样，定义统一的**工具发现 + 调用协议**。任何 MCP server 暴露的工具，都能被任何 MCP client（Agent）使用。

```
┌──────────┐                    ┌─────────────┐
│  Agent   │  ── MCP 协议 ──→  │ MCP server  │
│ (client) │  ←─ JSON-RPC ──    │ (工具集合)   │
└──────────┘                    └─────────────┘
  任何框架                          任何语言
```

### 三大原语

- **Tools**：可调用函数（最常用）
- **Resources**：可读数据（文件式）
- **Prompts**：可复用提示模板

### 两种传输

- **stdio**：本地子进程（最常用），走管道有序列化开销但简单
- **http**（streamable-http）：远程跨网络

### 本项目怎么用 MCP

**双向**——既是 client 又是 server。

**作为 Client**（`app/mcp/client.py`）：
1. 读 `mcp_servers.json` 配置
2. 用 `MultiServerMCPClient` 连接各外部 server
3. 发现的工具统一转成 LangChain BaseTool（`langchain-mcp-adapters`）
4. 塞进 Agent 工具注册表

```python
class MCPClientManager:
    async def connect(self):
        servers = self._load_servers_config()
        self._client = MultiServerMCPClient(servers)
        self._tools = await self._client.get_tools()  # 发现工具
        self._connected = True
```

设计要点：
- **单个 server 连不上不阻断其他**（优雅降级，和 db_manager 一致）
- **工具按 server名_工具名 前缀防命名冲突**
- **懒加载**：首次 get_tools() 才真正连接

**作为 Server**（`app/mcp/server.py`）：
```python
mcp = FastMCP("self-agent-tools")

@mcp.tool()
def some_tool(...):
    ...
```

把本 Agent 工具暴露出去供其他 Agent 调用。两种启动：`python -m app.mcp.server`（stdio）/ `--http`（远程）。

### ★ 版本锁定决策（真实工程权衡）

`pyproject.toml` 里 `mcp>=1.24.0,<2.0`，**锁 1.x 不用 2.0**。原因：

- `langchain-mcp-adapters 0.3.1` 仍使用 mcp 1.x 的 `RequestContext`，**尚未适配 mcp 2.0**
- 强行用 2.0 会导入崩溃
- 待官方适配后解除上限

教训：「追新不能违背兼容性现实」。这是工程诚实——不为了「用最新版」而引入崩溃。

### 为什么用 langchain-mcp-adapters 不自己写

官方维护、经过测试、返回标准 BaseTool 无缝接入 LangGraph。自己写要处理 MCP 协议细节（会话、JSON-RPC、schema 转换）约 150 行，没必要重复造轮子。

## 10.3 A2A（Agent2Agent Protocol）

Google 2025 年发布、后移交 Linux Foundation 的标准。让**不同框架/厂商**的 Agent 互相发现、通信、协作。

### MCP vs A2A（最常考的对比）

| 维度 | MCP | A2A |
|---|---|---|
| 通信方 | agent ↔ **工具** | agent ↔ **agent** |
| 对方 | 被动（工具无自主决策） | **对等**（双方都有 LLM、记忆、工具） |
| 类比 | USB-C 工具接口 | HTTP |
| 发现 | host 主动连 server（中心化） | `/.well-known/agent-card.json`（去中心化，DNS 式） |

**互补不互斥**：MCP 管 agent 怎么用工具，A2A 管 agent 怎么找别的 agent。

### 核心概念

- **Agent Card**：JSON 名片，描述 agent 的能力/技能/端点/鉴权，放在 `/.well-known/agent-card.json`
- **Task**：工作单元，状态机 `submitted → working → completed`
- **Message**：一轮对话，含 role 和 Parts
- **Part**：内容块（text / data / file）
- **传输**：JSON-RPC 2.0 over HTTP，流式用 SSE

### 本项目怎么用 A2A

**双向**——既是 server 又是 client。

**作为 Server**（`app/a2a/server.py`）：`mount_a2a(app)` 把路由挂到 FastAPI。`SelfAgentExecutor`（`a2a/executor.py`）把 `run_agent` 包装成 A2A 任务执行器——别的 Agent 可以通过 A2A 协议调用本 Agent。

**作为 Client**（`app/a2a/client.py`）：`call_remote_agent(base_url, message)`。还有 `delegate_to_agent` 工具——LLM 自主决定何时把任务委托给外部 Agent。

```
用户：「帮我翻译这段话并总结」
  ↓
本 Agent：识别需要翻译 → delegate_to_agent("http://translator:8001", 原文)
  ↓
翻译 Agent：返回译文
  ↓
本 Agent：拿到译文 → 整合总结 → 回复用户
```

### 不透明对等体

A2A 的核心设计：Agent 间**共享输入输出，不共享内部**（工具、记忆、状态）。保证解耦——不需知道对方用什么框架/LLM。像 HTTP 让任意服务器互通一样。

### delegate_to_agent 的安全考量

委托外部 Agent 的风险：信任与安全。无法保证输出质量/安全。生产应加：超时控制、输出校验、白名单（只委托可信 Agent）、审计日志。当前实现已有超时（60s）和错误兜底。

代码：`app/a2a/`。

## 10.4 Skill 系统

`app/skills/`。把「工具 + 提示词 + 元数据」打包成**可插拔能力单元**。

### 为什么需要 Skill（三个痛点）

1. **工具表臃肿**：几十个工具堆一起，LLM 选择成本上升、易选错（context 污染）
2. **提示词无法配套**：工具是「怎么做」，但「该用什么语气/策略」无处安放
3. **难以复用**：能力散落各处无法整体移植

### Skill vs Tool vs MCP

| 概念 | 粒度 | 关注点 |
|---|---|---|
| Tool | 单个原子操作 | 「怎么做」一个具体动作 |
| MCP | 传输协议 | 工具「怎么传递」（本地/远程/跨进程） |
| Skill | 能力单元 | 「组合哪些工具 + 用什么策略」（业务编排层） |

层次：Skill（业务能力）下挂 Tool A（内置）、Tool B（MCP）+ 提示词。

### Skill 的组成

```python
@skill
class MathAssistant(SkillBase):
    meta = SkillMeta(name="math_assistant", description="高级数学", enabled_by_default=True)
    tools = [advanced_math]   # 工具集（可含本地 @tool 和 MCP 远程工具）
    prompt = "你是数学专家……"  # 提示词片段
```

`@skill` 装饰器声明式注册到 `skill_registry`。

### 加载流程

```
应用启动
  ├─ import app.skills.builtin  # 触发 @skill 注册
  ├─ skill_registry.load_all_defaults()
  │     ├─ 对每个 enabled_by_default 的 Skill：
  │     │   ├─ 调 on_load()              # 初始化钩子
  │     │   ├─ register_tools(skill.tools)  # 工具 → Agent 注册表
  │     │   └─ 标记为 loaded
  │     └─ Skill 提示词在 _build_system_prompt 时拼进系统提示
```

### 提示词注入

Skill 的 prompt 在 `_build_system_prompt()`（`graph.py:74`）时拼进系统提示：

```python
for name in skill_registry.loaded_names:
    s = skill_registry.get(name)
    if s and s.prompt:
        skill_prompts.append(s.prompt)
if skill_prompts:
    base = base + "\n\n" + "\n\n".join(skill_prompts)
```

代码：`app/skills/`。

## 10.5 一个 Agent 的三种角色

本项目同时扮演：

```
┌─ MCP client（用外部工具）
├─ MCP server（被外部用工具）
├─ A2A server（被外部 Agent 调用）
├─ A2A client（调用外部 Agent）
└─ Skill 容器（封装能力单元）
```

这就是「协议驱动」的 Agent——不靠单一框架，靠标准协议接入生态。

## 10.6 外部世界怎么做

| 协议 | 状态 |
|---|---|
| **MCP** | 2024 末 Anthropic 开源，已成事实标准。Cline/Cursor 等都原生支持 |
| **A2A** | 2025 Google → Linux Foundation，规范化中 |
| **OpenAI handoffs** | OpenAI 自己的 Agent 间转交机制（非开放标准） |
| **AutoGen GroupChat** | AutoGen 自己的群聊协作（非开放标准） |

**趋势**：MCP 让工具层 provider-agnostic，A2A 让 Agent 层 framework-agnostic。详见拆解③。

## 10.7 面试一句话

> **Q：MCP 和 A2A 的本质区别？**
> A：MCP 是 agent↔tool（工具被动，无自主决策），A2A 是 agent↔agent（双方都有 LLM/记忆/工具，对等）。一个 Agent 可同时是 MCP client + A2A server + A2A client。

> **Q：Skill 和 Tool 什么关系？**
> A：Tool 是单个原子操作（「怎么做」），Skill 是能力单元（「组合哪些工具 + 用什么策略」）。Skill 下挂多个 Tool + 配套提示词，是业务编排层。
