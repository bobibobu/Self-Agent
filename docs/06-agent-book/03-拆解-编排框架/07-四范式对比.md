# 第 7 章：多 Agent 四范式对比

> 这是本系列最值得记住的对比——**多 Agent 协作的四种隐喻**。
> 把前面几章的 handoff / GroupChat / 角色 / A2A 拉到一张表上，看清本质区别。

---

## 7.1 四种「多人协作」隐喻

| 范式 | 代表 | 隐喻 | 特点 | 适用 |
|---|---|---|---|---|
| **群聊** | AutoGen GroupChat | 开会讨论 | 多 agent 围绕共享对话轮流发言 | 协作讨论、多视角 |
| **接力** | OpenAI handoffs | 控制权转移 | A 退出 B 接管，上下文迁移 | 任务分流、专家转交 |
| **剧本角色** | CrewAI / MetaGPT | 戏剧角色 | 每个 agent 有 role/goal/backstory | 模拟团队、SOP |
| **任务委派** | **A2A（Self-Agent）** | 派工单 | 对等体，标准协议，不透明 | 跨框架、解耦协作 |

---

## 7.2 范式①：群聊（AutoGen GroupChat）

### 怎么工作

多个 agent 围绕一个**共享对话**轮流发言。有 selector 决定下一个谁发言。

### 优势

- **多视角融合**：不同角色从不同角度发言，最终收敛
- **直觉**：像人类开会

### 劣势

- **对话历史膨胀**：agent 多了，历史爆炸
- **同步低效**：轮流等待
- **扩展性差**：AutoGen 因此走向维护模式

### 适合

需要多视角融合的开放讨论（如「设计一个系统」让 PM/架构师/工程师各抒己见）。

---

## 7.3 范式②：接力（OpenAI handoffs）

### 怎么工作

A agent 把**整个对话控制权**交给 B agent，A 退出，B 接管。上下文随之迁移。

### 优势

- **专家转交**：通用 agent 遇到专业问题，handoff 给专家
- **简单**：A 不用等 B 返回，直接退出

### 劣势

- **不可逆**：A 退出后不能拿回控制权
- **guardrail 盲区**：工具级 guardrails 不作用于 handoff

### 适合

明确的任务分流（客服 → 技术支持 → 售后），每个环节专家接管。

---

## 7.4 范式③：剧本角色（CrewAI / MetaGPT）

### 怎么工作

每个 agent 有 role/goal/backstory，像剧本角色。Crew 编排它们的协作（sequential/hierarchical）。

### 优势

- **直觉化**：非技术人能懂
- **目标明确**：role/goal 约束 agent 行为
- **可复用**：角色定义可移植

### 劣势

- **绑框架**：CrewAI 角色是自有抽象，不跨框架
- **流程固化**：SOP 写死，不够动态

### 适合

模拟团队（MetaGPT 的软件公司）、SOP 流程（CrewAI）。

---

## 7.5 范式④：任务委派（A2A，Self-Agent）

### 怎么工作

A agent 通过标准协议（A2A）给 B agent **派工单**，B 返回结果，A 继续。双方对等，不共享内部。

### 优势

- **标准化**：开放标准，不绑框架
- **解耦**：不透明对等体，任意实现互通
- **去中心化发现**：`/.well-known/agent-card.json`

### 劣势

- **重**：双方都要实现协议
- **协作质量依赖 agent 能力**：协议不管流程质量

### 适合

跨框架、跨组织的协作（如你的 agent 委托外部翻译 agent）。

---

## 7.6 ★ Self-Agent 为什么选 A2A

Self-Agent 的多 Agent 协作用 A2A（任务委派）。原因：

1. **标准化**：开放标准（Google/Linux Foundation），不绑框架。未来要和别的 agent 协作，A2A 是通用语言。
2. **解耦**：不透明对等体，不共享内部。委托方不需要知道被委托方用什么 LLM/工具/存储。
3. **去中心化发现**：Agent Card 放 `/.well-known/`，DNS 式发现，不需要中心注册。
4. **与 MCP 互补**：MCP 管 agent↔tool，A2A 管 agent↔agent。一个 agent 可同时是 MCP client + A2A server + A2A client。

### 代价

- 比 handoff/GroupChat 更「重」——双方都要实现协议
- 适合需要**跨框架协作**的场景；如果都是自家人，CrewAI 角色化或 AutoGen 群聊更轻

---

## 7.7 怎么选范式

| 你的场景 | 推荐范式 |
|---|---|
| 需要多视角融合的开放讨论 | 群聊（AutoGen） |
| 明确的任务分流、专家转交 | 接力（OpenAI handoffs） |
| 模拟团队、SOP 流程 | 剧本角色（CrewAI/MetaGPT） |
| 跨框架、跨组织协作 | 任务委派（A2A） |
| 同框架内、需直觉表达 | 剧本角色（CrewAI） |

**Self-Agent 的选择**：A2A（任务委派）+ delegate_to_agent 工具。因为定位是「可部署服务」，需要和外部 agent 协作，标准化协议最合适。

---

## 7.8 一个观察：范式在融合

实际产品里，范式不是互斥的：
- OpenAI SDK 同时支持 handoff 和 agents-as-tools（两种模式可选）
- Self-Agent 的 delegate_to_agent 既能「委派拿结果」（delegate）也能设计成「转交」（handoff）
- CrewAI 的 hierarchical 本质是 router（第四种范式）

**趋势**：多范式共存，按场景选。
