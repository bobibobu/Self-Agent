# 性能基准与压测报告

> 2026-08-14 实测。工具：`scripts/benchmark.py`（框架层，mock LLM）+ 真实 GLM（glm-4.5-flash）端到端测试。
> 环境：Windows 10 / Python 3.12 / 单进程单事件循环（= uvicorn 单 worker 等价）/ DB 未起走内存兜底。

---

## 1. 一句话结论

- **框架层 QPS**：新会话稳态 **~680 rps**，长会话（含上下文压缩 + checkpoint）**~475 rps**，流式 **~400-500 rps**（mock LLM 0ms，单 worker）；
- **真实瓶颈在 LLM**：接真实 GLM 后并发 10 只有 **~2.5 rps**，p50 ≈ 2.6s——框架开销（<15ms）占不到 1%，加 worker 无法提升，要提吞吐只能换快模型 / 加 provider 并发额度；
- **本轮优化**（工具 Schema 缓存 / 摘要缓存 / 提示词缓存）：长会话吞吐 **+27%**，p50 **-33%**，长会话每轮少 1~2 次摘要 LLM 调用（真实 token 成本下降）。

---

## 2. 框架层基准（mock LLM 0ms，隔离 LLM 延迟）

| 场景 | 吞吐 | p50 | p95 | p99 |
|---|---:|---:|---:|---:|
| GET /health（并发32） | 5,430 rps | 0.2ms | 0.3ms | 0.6ms |
| GET /tools（并发32） | 5,160 rps | 0.2ms | 0.3ms | 0.5ms |
| GET /sessions（并发32） | 4,368 rps | 0.2ms | 0.3ms | 0.5ms |
| POST /chat 新会话 并发8 | **680.7 rps** | 10.7ms | 12.2ms | 13.5ms |
| POST /chat 新会话 并发32 | 597.9 rps | 36.4ms | 99.0ms | 103.3ms |
| POST /chat 新会话 并发64 | 557.4 rps | 79.9ms | 143.3ms | 152.6ms |
| POST /chat 长会话 并发8 | **474.8 rps** | 13.5ms | 20.7ms | 22.0ms |
| POST /chat/http-stream 并发16 | ~400-500 rps | ~30ms | ~90ms | — |
| POST /chat 并发50（mock LLM 500ms） | 85.9 rps | 549.8ms | 575.5ms | 615.7ms |

说明：
- **新会话** = 每请求独立 thread_id，历史恒为 1 轮 → 稳态框架开销；
- **长会话** = 共用 thread_id，历史随请求数增长（100 轮），含上下文压缩与 checkpoint 读写；
- 500ms mock 那行验证并发能力：50 并发下框架只增加 ~50-70ms 排队开销，事件循环不是瓶颈；
- 内存 checkpointer；连 Postgres 后每请求额外 +5~20ms（见 §5 注意事项）。

### 优化前后对比（同口径：长会话 ×100 并发8）

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 吞吐 | 373.7 rps | 474.8 rps | **+27%** |
| p50 | 20.0ms | 13.5ms | **-33%** |
| p95 | 25.0ms | 20.7ms | **-17%** |

优化前还有个反直觉现象：并发 8→64 吞吐从 374 一路掉到 234（CPU 密集段串行化）。优化后新会话场景 680→557，衰减坡度明显变缓。

## 3. 真实 LLM 端到端（GLM glm-4.5-flash，走真实 TCP）

| 指标 | 数值 |
|---|---|
| 非流式 /chat e2e | 2.0 ~ 4.5s（p50 ≈ 2.3s） |
| 流式 TTFT（首字延迟） | **1.8 ~ 2.8s**（首轮含连接建立） |
| token 间隔 | ~27ms（≈37 token/s，模型侧出词速度） |
| 并发 10 × 20 请求 | 2.5 rps，p50 2.6s，max 4.7s，零错误 |

解读：
- TTFT 里框架只占 <15ms，其余全是 GLM 侧（网络 + 排队 + prefill）。系统提示 + 14 个工具 Schema 会让 prefill 变大——好在项目已做 prompt 缓存前缀设计（系统提示静态化），命中缓存后 prefill 成本下降；
- **测流式必须走真实 TCP**：httpx 的 `ASGITransport` 会缓冲整个响应体，进程内测出的 TTFT ≈ 总耗时，是假象；
- 真实场景的容量上限 = min(provider 限额, 框架 QPS)。对 glm-4.5-flash 单 key 而言 provider 是瓶颈，水平扩 uvicorn worker 无收益，应先升 provider 并发额度或加 key 池。

## 4. 本轮实施的优化（2026-08-14）

| # | 位置 | 问题 | 修法 | 收益 |
|---|---|---|---|---|
| 1 | `app/agent/nodes/bridge.py` | 每次 LLM 调用重新生成 14 个工具的 Pydantic JSON Schema（占热路径 ~18% CPU） | 按 (name, description, schema类) 缓存；schema 换类自动失效 | 吞吐 +27%（长会话同口径） |
| 2 | `app/agent/context_manager.py` | 长会话每轮 / ReAct 循环每次回到 agent 都全量重摘一次（多 1~2 次摘要 LLM 调用/轮） | 按 thread 缓存摘要 + 迟滞窗口（攒 6 条才增量摘一次）；边界消息 id 校验防错配 | 真实 LLM 下长会话每轮少 1~2 次 LLM 调用（token + 延迟双降） |
| 3 | `app/evolution/prompt_store.py` | 每请求同步读盘 + JSON 解析提示词文件 | (mtime_ns, size) 校验缓存，写入自动失效 | 每请求省一次磁盘 IO |
| 4 | `scripts/benchmark.py` | 日志刷屏、Jaeger 未起时 OTEL 导出重试拖慢收尾、长会话/新会话场景混在一起 | 默认关 OTEL + WARNING 日志；拆"新会话/长会话"两种场景 | 基准可重复、结果可读 |

踩坑记录（有价值）：工具 Schema 缓存第一版 key 用了 `type(args_schema)`——**所有 Pydantic 模型的元类都是同一个 `ModelMetaclass`**，导致缓存永不失效（MCP 换 Schema 也不刷新）。被 `tests/test_perf_optimizations.py` 的失效用例当场拦截。教训：缓存 key 必须能区分"数据变没变"，元类区分不了模型类。

回归测试：`tests/test_perf_optimizations.py` 11 个用例；全套 184 passed / 6 skipped。

## 5. 注意事项与后续可做的优化

**运维注意（不是代码问题）**：

1. **Jaeger 未起时别开 OTEL**：`OTEL_ENABLED=true` 但 4318 端口无人监听 → 导出器反复重试、刷 WARNING、拖慢进程收尾。要么起 `infra/docker-compose.yml` 里的 Jaeger，要么关掉。
2. **Windows + psycopg**：uvicorn 在 Windows 默认 ProactorEventLoop，psycopg 异步不支持 → 连接池初始化失败，静默回退 MemorySaver（首个请求多吃 5s 超时）。生产部署在 Linux/Docker 无此问题；本地 Windows 调试要有心理预期（日志有 WARNING）。（**2026-10 已修**：见 `app/core/eventloop.py`，Windows 上用 Selector 循环）
3. **多 worker 部署时内存 checkpointer 不共享**：跨 worker 会话漂移。生产必须连 Postgres checkpointer（每请求 +5~20ms，但吞吐仍有几百 rps 空间）。

**后续可做（按性价比排序）**：

1. **多 worker / 多实例横向扩**：框架 QPS 单 worker 已 500+，4 worker 就是 2000+——但先确认真实瓶颈是 provider，否则白扩；
2. **LLM key 池 + 客户端侧限流**：真实吞吐卡在 provider 并发额度（2.5 rps@10并发），多 key 轮询是唯一有效的横向扩手段；
3. **`/sessions`、`/tools` 等只读端点加 ETag/Cache-Control**：内网场景可再省一截（当前 4-5K rps，一般够用）；
4. **checkpoint 序列化**：超长会话（几百轮）时 MemorySaver 读全量历史是 O(历史长度)，可考虑 LangGraph 官方 Postgres saver 的增量写（已在用官方 AsyncPostgresSaver 的话天然解决）；
5. **摘要阈值调优**：`DEFAULT_MAX_MESSAGES=20 / KEEP_RECENT=10 / _COMPRESS_EVERY=6` 目前是拍脑袋值，可按真实 token 分布（对话日志里有 usage）回归调参。
